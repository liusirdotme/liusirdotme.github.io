Redis-Memcached-MongoDB

  1. Redis
  • 优点
    • 支持多种数据结构，如string/list/hashes/set/zset/hyperloglog/simply bitmaps/streams
    • 支持持久化操作
    • 支持通过Replication进行数据复制，通过master-slave机制，可以实时进行数据的同步复制，支持多级复制和增量复制，master-slave机制是Redis进行HA的重要手段。
    • 单线程请求，所有命令串行执行，并发情况下不需要考虑数据一致性问题。
    • 支持pub/sub消息订阅机制，可以用来进行消息订阅与通知。
    • 支持简单的事务
  • 缺点
    • Redis只能使用单线程，性能受限于CPU性能，故单实例CPU最高才可能达到5-6wQPS每秒（取决于数据结构，数据大小以及服务器硬件性能，日常环境中QPS高峰大约在1-2w左右）。
    • 支持简单的事务需求，但业界使用场景很少，并不成熟，既是优点也是缺点。
    • Redis在string类型上会消耗较多内存，可以使用dict（hash表）压缩存储以降低内存耗用。
    • Mc和Redis都是Key-Value类型，不适合在不同数据集之间建立关系，也不适合进行查询搜索。比如redis的keys pattern这种匹配操作，对redis的性能是灾难。
  1. Memcached
  • 优点
    • Memcached可以利用多核优势，单实例吞吐量极高，可以达到几十万QPS（取决于key、value的字节大小以及服务器硬件性能，日常环境中QPS高峰大约在4-6w左右），适用于最大程度扛量。
    • 支持直接配置为session handle。
  • 缺点
    • 只支持简单的key/value数据结构，不像Redis可以支持丰富的数据类型。
    • 无法进行持久化，数据不能备份，只能用于缓存使用，且重启后数据全部丢失。
    • 无法进行数据同步，不能将Memcached中的数据迁移到其他MC实例中。
    • Memcached内存分配采用Slab Allocation机制管理内存，value大小分布差异较大时会造成内存利用率降低，并引发低利用率时依然出现踢出等问题，故需要用户注重value设计。
  1. mongoDB
  • 优点
    • 更高的写负载，MongoDB拥有更高的插入速度。
    • 处理很大的规模的单表，当数据表太大的时候可以很容易的分割表。
    • 高可用性，设置M-S不仅方便而且很快，MongoDB还可以快速、安全及自动化的实现节点（数据中心）故障转移。
    • 快速的查询，MongoDB支持二维空间索引，比如管道，因此可以快速及精确的从指定位置获取数据。MongoDB在启动后会将数据库中的数据以文件映射的方式加载到内存中。如果内存资源相当丰富的话，这将极大地提高数据库的查询速度。
    • 非结构化数据的爆发增长，增加列在有些情况下可能锁定整个数据库，或者增加负载从而导致性能下降，由于MongoDB的弱数据结构模式，添加1个新字段不会对旧表格有任何影响，整个过程会非常快速。
    • 适合场景：事件记录、内容管理或博客平台
  • 缺点
    • 不支持事务
    • MongoDB占用空间过大
    • MongoDB没有成熟的维护工具
  • mongodb持久化原理
    • ysql的每一次更新操作都会直接写入硬盘
    • mongodb启动时会专门初始化一个线程不断循环，用于在一定时间周期内来从defer队列中获取要持久化的数据并写入到磁盘的journal(日志)和mongofile(数据)处。因为它不是在用户添加记录时就写到磁盘上，所以mongodb开发者说它不会造成性能上的损耗。
    • 当进行CUD操作时，记录(Record类型)都被放入到defer队列中以供延时批量提交写入，其中时间周期参数是个要认真考量的参数，系统默认为90毫秒，如果该值更低的话可能会造成频繁磁盘操作，过高又会造成系统宕机时数据丢失过。
  1. Redis VS Memcached
  • Redis只使用单核，而Memcached可以使用多核，在大量数据处理性能上比Memcached稍差。
  • MemCached可以修改最大内存，采用LRU算法；Redis增加了VM的特性，突破了物理内存的限制。
  • MemCached数据结构单一，仅用来缓存数据；而Redis支持更加丰富的数据类型，也可以在服务器端直接对数据进行丰富的操作从而减少网络IO次数和数据体积。
  • MemCached不支持数据持久化，断电或重启后数据消失，但其稳定性是有保证的；Redis支持数据持久化和数据恢复，允许单点故障，但是同时也会付出性能的代价。
  • Memcached适用于动态系统中减轻数据库负载，提升性能；做缓存，适合多读少写，大数据量的情况(如人人网大量查询用户信息、好友信息、文章信息等)； Redis适用于对读写效率要求都很高，数据处理业务复杂和对安全性要求较高的系统(如新浪微博的计数和微博发布部分系统，对数据安全性、读写要求都很高)。
  • Memcached单个key-value大小有限，一个value最大只支持1MB；而Redis最大支持512MB。

Redis高频面试

一、基础概念与选型

Q1. 什么是 Redis？

Redis（REmote DIctionary Server）是用 ANSI C 编写的开源、BSD 协议的内存型 key-value 数据库。

  • 数据常驻内存，单机可支撑 10 万级 QPS、毫秒级以下延迟。
  • 支持 RDB/AOF 持久化、主从复制、Sentinel 高可用、Cluster 分片。
  • 命令处理是单线程（6.0 起网络 I/O 可多线程），靠 I/O 多路复用驱动事件循环。
  • 数据类型丰富，除缓存外还常用作 KV 存储、计数器、排行榜、分布式锁、轻量消息队列。

定位：它不是通用关系库的替代品，核心价值是”高并发 + 低延迟 + 丰富数据结构“。

Q2. Redis 相比 Memcached 有哪些优势？

  • 数据类型丰富：String/List/Hash/Set/ZSet/Bitmap/HLL/GEO/Stream；Memcached 只有 String。
  • 持久化：RDB + AOF；Memcached 纯内存，重启即丢。
  • 高可用与扩展：主从、Sentinel、Cluster 原生支持；Memcached 需客户端自己做分片。
  • 单 value 上限：512MB vs 1MB。
  • 支持事务、Lua、发布订阅、TTL 精细控制、范围查询与集合运算。
  • 内存管理：Redis 用 jemalloc + 自研编码；Memcached 用 slab allocator，固定 chunk 会浪费。
  • 协议与应用生态：RESP 协议简单，客户端与工具链成熟。
  • Memcached 的优势：多线程，纯 KV 大并发小对象场景下更能吃满多核；Redis 单实例是单线程（可用多实例弥补）。

Q4. Redis 主要消耗什么物理资源？

内存是第一资源，也是容量与成本的边界。

  • 内存：数据、redisObject、哈希表、复制积压缓冲、客户端缓冲、碎片。
  • 网络带宽：大 value、批量拉取、全量同步时会成为瓶颈（千兆网卡仅 125MB/s）。
  • CPU：通常不是瓶颈（单线程），但复杂命令、大 key 序列化、Lua 长脚本会打满单核。
  • 磁盘：只用于持久化落盘（RDB 快照、AOF 追加、fork 写时复制），一般不是性能瓶颈，但 fsync 抖动会影响延迟。

Q5. Redis 的全称是什么？

REmote DIctionary Server（远程字典服务器）。

Q7. Redis 官方为什么不提供 Windows 版本？

官方只正式支持 Linux/Unix（含 macOS、*BSD），原因：

  1. fork + 写时复制是 RDB 快照与 AOF 重写的核心机制，Windows 没有 fork 语义，无法低成本复制进程内存视图。
  2. 事件循环依赖 epoll/kqueue，Windows 只有 IOCP/select，IOCP 是完成端口模型，与 Redis 的 reactor 架构差异大，select 有 1024 fd 上限且性能差。
  3. 内存分配（jemalloc）、透明大页、fork 后的 COW 行为在 Windows 上表现不同，难以保证延迟特性。
  4. 目标用户与服务端部署环境以 Linux 为主，维护两套实现性价比低。

替代方案：WSL2、Docker Desktop、Memurai（商业兼容版）、微软早期维护的 3.2 移植版（已停更）。

Q8. 一个字符串类型的值能存储的最大容量是多少？

512MB（proto-max-bulk-len 默认 512mb，SDS 头用 size_t 记录长度，但协议与实现约定该上限）。

实践建议：单 value 控制在 10KB 以内，越小越好。大 value 会让单线程阻塞在序列化/网络回写上，MGET 时更会瞬间打满带宽，fork 时 COW 放大也更明显。

Q9. 为什么 Redis 需要把所有数据放到内存中？

核心是速度数量级差异：

  • 内存随机访问约 100ns，SSD 随机读约 50–100μs，机械盘寻道是 ms 级——差 3~4 个数量级。
  • Redis 是单线程事件循环，任何一个命令的磁盘 I/O 都会阻塞全站，只能在内存里做。
  • 数据结构可以直接用指针（跳表、哈希表、双向链表），不需要为磁盘页设计 B+ 树式布局，代码简单、延迟可预测。

代价：内存贵、容量受单机限制、断电易失，因此需要持久化与副本补偿。超内存数据集的场景（TB 级）通常选 Pika、Kvrocks 这类”Redis 协议 + RocksDB 存储”的方案，而不是原生 Redis。

Q13. Redis 有哪些适合的场景？

  • 缓存：对象缓存、页面缓存、会话共享、多级缓存。
  • 排行榜 / 榜单：ZSet 天然有序，O(logN) 插入与范围查询。
  • 计数器与限流：INCR、INCRBY、过期窗口、令牌桶（Lua）。
  • 分布式锁：SET key val NX PX + Lua 释放，Redisson 看门狗续期。
  • 消息队列：Stream（支持消费组、ACK）、List（轻量队列）、ZSet（延时队列）。
  • 发布订阅：轻量广播（不持久、不保证送达）。
  • 地理位置：GEO（底层 ZSet + GeoHash），附近的人、距离计算。
  • 位图类：签到、在线状态、布尔标记（Bitmap）；UV 估算（HyperLogLog）。
  • 去重与标签：Set、布隆过滤器（RedisBloom）。
  • 购物车 / 对象属性：Hash。
  • 最新 N 条 / 时间线：List + LTRIM。

Q40. Redis 与其他 key-value 存储有什么不同？

  • 数据结构：不只是 KV，还有容器类型与位图/基数/地理/流类型，能在服务端完成集合运算、排序、范围查询。
  • 持久化 + 复制 + 集群三位一体，既是缓存也能当轻量存储。
  • 原子性模型：单线程串行执行，单命令天然原子，配合 MULTI/Lua 做组合原子。
  • TTL 与内存淘汰内建，适合缓存生命周期管理。
  • 单线程 + 事件驱动，延迟稳定、无锁竞争。
  • 协议简单（RESP）、生态成熟（客户端、代理、监控、迁移工具齐全）。

Q41. Redis 的内存占用情况怎么样？

一个 key 的基础开销：

  • redisObject 16 字节 + SDS 头（sdshdr8 约 3–9 字节）+ 内容
  • dictEntry 24 字节 + key 指针 + value 指针
  • 哈希表按 2 的幂扩容，负载因子 ~1，实际有一倍冗余空间
  • jemalloc 按 size class 对齐（8/16/32/48/64…），有内部碎片

经验值：每个短 key 的基础开销约 80–120 字节。100 万个 key=10B、value=10B 的实例，实际占用约 100–150MB。

判断指标：mem_fragmentation_ratio = used_memory_rss / used_memory

  • >1.5 说明碎片较多，可开 activedefrag
  • <1 说明部分内存被 swap 出去了，必须立刻处理（延迟会飙升）

Q46. 一个 Redis 实例最多能存放多少 keys？List/Set/ZSet 最多多少元素？

  • 单实例 key 数理论上限 2^32（dict 的 size 是 32 位），实际受内存限制。
  • List、Set、ZSet、Hash 单个 key 最多 2^32−1 个元素。
  • 实践上要远远低于理论上限：单 key 元素建议控制在 1 万以内、总大小 1MB 以内，否则就是大 key。

二、数据类型与底层实现

Q3. Redis 支持哪几种数据类型？

5 种基础类型：String、List、Hash、Set、ZSet（Sorted Set）。

扩展类型：

  • Bitmap（位图，基于 String 的位操作）
  • HyperLogLog（基数估算，12KB 估 2^64 基数）
  • GEO（地理位置，底层 ZSet + GeoHash）
  • Stream（5.0 引入的消息流，支持消费组）
  • Bitfield（位域读写）

对应编码：

类型 编码
String int / embstr（≤44 字节）/ raw
List quicklist（listpack 节点 + 双向链表），7.0 后纯 listpack 结构
Hash listpack（原 ziplist）→ hashtable
Set intset（全整数且元素少）→ listpack（7.2）→ hashtable
ZSet listpack（元素少且短）→ skiplist + dict
Stream rax（基数树）+ listpack

Q56. Redis 有哪些原子命令？

  • 单条命令天然原子（单线程串行执行，不会被打断）：SET、GETSET、INCR/DECR/INCRBY、HINCRBY、SADD、LPUSH/RPOP、ZINCRBY、SETNX、HSETNX、EXPIRE。
  • 一条命令内的复合语义：SET key val NX PX 10000（互斥 + 过期一步完成，分布式锁基础）、SETEX、GETDEL、GETEX。
  • 多命令原子：MULTI/EXEC（原子执行但不回滚）、Lua 脚本（服务端整体执行，最常用）、Redis 7.0 的 FUNCTION。
  • 跨实例/跨槽没有原子性：Cluster 中多 key 必须同槽（hash tag），否则 CROSSSLOT。

Q57. Redis Cluster 哈希槽里面存的是啥？

槽（slot）只是 0–16383 的逻辑分区编号，本身不是容器，不存数据。

  • 每个节点维护 clusterState.slots[16384]，元素是指向 clusterNode 的指针，表示”这个槽归谁负责”。
  • 槽的归属由 CLUSTER ADDSLOTS / SETSLOT 维护，节点间通过 Gossip 同步槽位 bitmap。
  • 真实 key 仍以普通键值存在负责节点的 db 哈希表中，slot = CRC16(key) mod 16384 只是路由索引。
  • 迁移态用 migrating / importing 标记 + MIGRATE 按 key 搬运。

所以准确说：槽里存的是”槽 → 节点”的映射关系，数据在节点自己的字典里。

Q59. Redis 基础数据类型的底层实现，为什么 ZSet 用跳表而不用树？

核心结构：

  • SDS（简单动态字符串）：记录 len/alloc，O(1) 取长度、二进制安全、预分配减少 realloc。
  • dict：双哈希表 + 渐进式 rehash（把扩容成本摊到每次操作，避免单次卡顿）。
  • listpack / ziplist：连续内存 + 变长编码，小集合省内存（无指针开销）。
  • intset：有序整数数组 + 二分查找。
  • quicklist：双向链表串多个 listpack，兼顾内存与插入效率。
  • skiplist：多层索引链表，平均 O(logN) 查找。

ZSet = dict + skiplist 双结构：dict 存 member → score 做 O(1) 查分，skiplist 存有序序列做范围查询与排名（ZRANGE、ZRANK）。小数据量时退化为 listpack 单结构。

为什么不用红黑树/平衡树：

  1. 范围查询更自然：定位起点后在底层链表顺序遍历，指针跳转少、缓存友好；树做中序遍历要反复回溯父节点。
  2. 实现简单：插入删除只改前后指针，没有旋转、分裂、再平衡，代码量小、bug 面小，维护成本低。
  3. 无需再平衡开销：层高按 1/4 概率提升，期望 O(logN)，最坏 O(N) 但概率极低；树每次插删都可能触发旋转。
  4. 单线程下树的并发优势用不上，反而平衡维护是纯开销。
  5. 代价是指针开销（平均每节点 1.33 个指针），比红黑树（2 个）还略省，内存可接受。

三、内存管理与淘汰

Q6. Redis 有哪几种数据淘汰策略？

3.0 有 6 种，4.0 增加 LFU 后共 8 种：

策略 含义
noeviction 默认，不淘汰，写满返回 OOM 错误
allkeys-lru 所有 key 中按近似 LRU 淘汰
allkeys-lfu 所有 key 中按访问频次淘汰（4.0+）
allkeys-random 所有 key 中随机淘汰
volatile-lru 只在设置了过期时间的 key 中按 LRU
volatile-lfu 只在过期集合中按 LFU
volatile-random 只在过期集合中随机
volatile-ttl 优先淘汰剩余 TTL 最短的

选型：

  • 纯缓存 → allkeys-lru（或 allkeys-lfu，对”长期热、短期冷”更友好）
  • 缓存与持久数据混部 → volatile-*（保证无 TTL 的数据不被淘汰）
  • 数据不能丢 → noeviction + 容量告警 + 扩容
  • maxmemory 必须低于物理内存，给 fork 的 COW 和碎片留余量（一般设物理内存的 60%–70%）

Q12. MySQL 有 2000w 数据，Redis 只存 20w，如何保证 Redis 里都是热点数据？

目标是让 20w 容量自动收敛到热点集合，而不是靠人工挑：

  1. 选对淘汰策略：allkeys-lru 或 allkeys-lfu。热点问题优先 LFU：lfu-log-factor 调大让计数增长变慢、lfu-decay-time 控制衰减周期，避免”曾经热过一次”的 key 长期占位。
  2. 缓存预热：上线/低峰期按历史访问日志把 Top N 灌入，TTL 打散避免同时失效。
  3. 多级缓存：L1 本地缓存（Caffeine/Guava）挡住超热 key，L2 Redis，miss 回源 MySQL 并回填（回填带随机 TTL 防雪崩）。
  4. 主动识别热点：业务埋点或采样统计访问次数，写入 ZSet，定时任务把高频 key 提升、低频 key 降级/不缓存；也可用 redis-cli --hotkeys（依赖 LFU）观察。
  5. 防穿透/击穿：布隆过滤器挡不存在的 key、空值短 TTL 缓存、热点 key 用逻辑过期或互斥重建。
  6. 观测闭环：keyspace_hits/keyspace_misses、命中率、evicted_keys，命中率低说明容量或策略要调。

Q29. Redis 如何做内存优化？

  • 缩短 key 与 value：key 用统一前缀 + 短标识，避免超长业务串。
  • 小对象合并：多个小 String 合成一个 Hash（省掉 N 个 redisObject 与 dictEntry，收益最大的一招）。
  • 用紧凑编码：hash-max-listpack-entries 128、hash-max-listpack-value 64、zset-max-listpack-entries 128、set-max-intset-entries 512，让集合走 listpack/intset。
  • 拆分大 key：Hash 按 id 取模分桶，List 按时间分段。
  • 用 Bitmap / HyperLogLog 替代大 Set：签到、UV 场景内存可降 1–2 个数量级。
  • 设过期时间，避免无界增长；用 UNLINK + lazyfree-* 异步释放。
  • 控制客户端缓冲：client-output-buffer-limit，防止慢消费者把内存吃光。
  • 碎片治理：activedefrag yes + active-defrag-ignore-bytes 100mb，或主从切换/重启整理。
  • 关闭透明大页（THP）：否则 fork 后 COW 以 2MB 为单位复制，内存与延迟双爆。
  • 小数据集（<4GB）可用 32 位实例，指针减半。
  • 业务侧压缩 value（protobuf/snappy），但要评估 CPU 成本。

Q30. Redis 回收进程如何工作的？

两条独立机制：

  1. 过期删除（针对设了 TTL 的 key）
    • 惰性删除：访问 key 时检查 expireIfNeeded，过期就删并返回空。
    • 定期删除：serverCron 每 100ms 随机抽 20 个带过期的 key，过期比例 >25% 就继续抽同一轮；6.0 起 active-expire-effort(1–10) 可调激进程度，避免过期 key 堆积。
  2. 内存淘汰（针对 maxmemory 上限）
    • 每次执行命令前（processCommand → performEvictions）检查 used_memory > maxmemory，超了就按策略随机采样 maxmemory-samples（默认 5）个 key，挑最该淘汰的删除，循环到降回阈值以下或无可淘汰。
    • 4.0 起支持 lazyfree：UNLINK、lazyfree-lazy-eviction、lazyfree-lazy-expire、lazyfree-lazy-server-del，把 free 放到后台 bio 线程，避免大 key 删除卡住主线程。

注意：从节点默认不主动淘汰（replica-ignore-maxmemory yes），等主节点删除后同步 DEL，保证主从一致。

Q31. Redis 回收使用的是什么算法？

  • 近似 LRU，不是严格 LRU：没有全局双向链表，而是每个 redisObject 里存 24 位 LRU 时钟（秒级精度），淘汰时随机采样 N 个 key，选 idle 最大的删。maxmemory-samples 越大越接近真实 LRU（5 已足够，10 更准但更耗 CPU）。
  • LFU（4.0）：8 位 Morris 概率计数器（0–255，lfu-log-factor 控制增长速度）+ 按分钟衰减（lfu-decay-time），解决”偶发访问被误判为热点”的 LRU 缺陷。
  • 另有 random 和 volatile-ttl（按剩余 TTL 升序）。

Q42. 都有哪些办法可以降低 Redis 的内存使用情况呢？

按性价比排序（多数可叠加使用）：

  1. 小 key 合 Hash（收益最大）：把同一对象的多个字段从 N 个 String 改成 1 个 Hash。10 个小 String → 1 个 Hash，可省掉 9 个 redisObject(16B) + 9 个 dictEntry(24B) + 冗余 SDS 头，实测常能省 50%–80%。
  2. 让集合走紧凑编码：hash-max-listpack-entries 128 / hash-max-listpack-value 64、zset-max-listpack-entries 128、set-max-intset-entries 512，元素少时用 listpack/intset，省掉全部指针。
  3. 用 Bitmap / HyperLogLog 替代 Set：签到、UV、布尔标记场景，内存可从”每用户 50B”降到”每位 1bit”或”每键 12KB”。
  4. 缩短 key 与 value：key 用短前缀（u:1001:pv 而非 user:1001:pageview），value 去掉冗余 JSON 字段。
  5. 拆分大 key：Hash 分桶、List 分段，既省峰值内存也避免 COW 放大。
  6. 设 TTL + 明确淘汰策略，杜绝无界增长；冷数据归档到 MySQL/对象存储。
  7. 控制客户端缓冲：client-output-buffer-limit normal 0 0 0、replica 256mb 64mb 60，慢消费者是隐形内存大户。
  8. 碎片治理：activedefrag yes、active-defrag-ignore-bytes 100mb，或主从切换/重启整理；mem_fragmentation_ratio 长期 >1.5 就必须处理。
  9. 业务侧压缩：value 用 protobuf/snappy/gzip 序列化，典型文本可压 3–5 倍（代价是 CPU）。
  10. 关闭透明大页：避免 fork 后 COW 以 2MB 页复制，既省内存也降延迟尖刺。
  11. 小实例可用 32 位编译（<4GB 数据），指针减半。
  12. 数据结构选型：用 ZSet 存”需要排序的少量数据”没问题，但别用 Set 存上亿布尔值；用 Stream 时配 MAXLEN 截断。

Q43. 查看 Redis 使用情况及状态信息用什么命令？

  • INFO：最核心。分段查看 INFO server（版本、运行时长、进程）、INFO clients（连接数、阻塞客户端）、INFO memory（used_memory、used_memory_rss、碎片率、mem_peak）、INFO persistence（RDB/AOF 状态、rdb_last_bgsave_status）、INFO stats（keyspace_hits/misses、evicted_keys、expired_keys、total_commands_processed、instantaneous_ops_per_sec）、INFO replication（角色、offset、从节点延迟）、INFO cpu、INFO cluster（cluster_state、槽分配）、INFO keyspace（各 db 的 key 数与过期数）。
  • 单 key 与内存明细：MEMORY USAGE key [SAMPLES n]、MEMORY STATS、MEMORY DOCTOR、OBJECT ENCODING key（看是否走了紧凑编码）、OBJECT FREQ key（LFU 计数）。
  • 慢查询与延迟：SLOWLOG GET 10、SLOWLOG LEN、SLOWLOG RESET、LATENCY DOCTOR、LATENCY HISTORY event。
  • 连接：CLIENT LIST、CLIENT INFO、CLIENT NO-EVICT。
  • 命令行工具：redis-cli --stat（实时概览）、--bigkeys（大 key 抽样）、--hotkeys（需 LFU）、--latency / --latency-history / --intrinsic-latency、--scan、--memkeys（内存维度的大 key）、MONITOR（排查用，生产慎开）。
  • 外部：Prometheus + redis_exporter、Grafana、云厂商监控面板。

Q44. Redis 的内存用完了会发生什么？

分两种情况：

  1. 设了 maxmemory（推荐）：
    • 非 noeviction 策略：按策略淘汰旧 key 腾空间，客户端无感知（但缓存命中率下降、可能淘汰掉本不该淘汰的数据）。
    • noeviction：写命令返回错误 OOM command not allowed when used memory > 'maxmemory'.，读命令仍正常；DEL 这类会释放内存的命令也允许执行。
    • 主从场景：从节点默认 replica-ignore-maxmemory yes 不淘汰，等主库的 DEL 同步；若主库 OOM 拒写，从库自然缺数据。
    • 危险点：maxmemory 设得过高（接近物理内存）时，fork 做 RDB/AOF 重写会因 COW 触发系统 OOM。
  2. 没设 maxmemory（危险）：
    • 内存一路涨到物理上限 → 触发 Linux OOM Killer 直接杀进程（可能杀掉 Redis 或别的服务）；
    • 或 fork 失败（Can't fork / Cannot allocate memory），导致 BGSAVE、AOF 重写、主从全量同步全部失败；
    • 中间态最难受：开始用 swap，延迟从 μs 级劣化到 ms–s 级，mem_fragmentation_ratio < 1 就是典型信号。

实践：maxmemory 设为物理内存 60%–70%，配淘汰策略与容量告警；used_memory 到 80% 就扩容或清理。

四、持久化

Q48. Redis 提供了哪几种持久化方式？

1. RDB（快照）

  • BGSAVE fork 子进程，利用写时复制生成某一时刻的全量二进制快照。
  • 触发：save 900 1 规则、SHUTDOWN、主从全量同步、DEBUG RELOAD。
  • 优点：文件紧凑（压缩）、恢复极快、适合冷备与跨机房拷贝。
  • 缺点：两次快照之间的数据会丢；fork 大实例会卡顿（内存翻倍风险）。

2. AOF（追加日志）

  • 把写命令追加到文件，重启时回放。
  • appendfsync：always（每条 fsync，最安全最慢）、everysec（每秒，最多丢 1s，默认）、no（交给 OS）。
  • BGREWRITEAOF 重写压缩（触发条件 auto-aof-rewrite-percentage 100 + auto-aof-rewrite-min-size 64mb）。
  • 7.0 改为 multi-part AOF：base（RDB 或 AOF 基线）+ incr（增量）+ manifest（清单），解决重写期间双写与磁盘占用问题。

3. 混合持久化（4.0+，aof-use-rdb-preamble yes）

  • AOF 文件前半段是 RDB 格式的全量，后半段是增量命令。重启时先加载 RDB 再回放增量，兼具”恢复快”与”丢得少”。

4. 无持久化：纯缓存部署，save "" + appendonly no。

Q49. 如何选择合适的持久化方式？

场景 建议
纯缓存，可全部重建 不开持久化，或只留 RDB 做冷备
一般业务，允许秒级丢失 AOF everysec + RDB 定期（RDB 做冷备/快速恢复，AOF 保数据完整度）
不允许丢数据（账务/订单关键态） AOF always + 独立 SSD + 主从 + 异地备份；更强一致性应以 MySQL 为准
大实例、重启要快 混合持久化（aof-use-rdb-preamble yes）

注意事项：

  • 主从复制不是备份，误删会同步到从库。
  • RDB 有版本兼容性（低版本加载不了高版本 RDB）。
  • fork 期间内存可能翻倍，单实例建议控制内存规模（一般 10–20GB 以内更稳）。
  • 持久化目录要与数据目录分离，定期把 RDB 拷到异地。

Q50. 修改配置不重启 Redis 会实时生效吗？

不一定，分三类：

  1. 支持 CONFIG SET 动态生效（并可用 CONFIG REWRITE 写回文件）：
    maxmemory、maxmemory-policy、maxmemory-samples、appendonly（可运行时开关）、appendfsync、save、slowlog-log-slower-than、slowlog-max-len、timeout、requirepass、masterauth、client-output-buffer-limit、各类 *-max-listpack-entries 等编码阈值（只影响后续新建的 key）、lazyfree-*、hz、io-threads、activedefrag。
  2. 改了不重启也”部分生效”：编码阈值只对新 key 生效，老 key 不重新编码；databases 改了无效。
  3. 必须重启（或重建实例）：port、bind、daemonize、pidfile、logfile、appendfilename、cluster-enabled、cluster-config-file、databases、supervised 等启动期参数。

验证姿势：CONFIG SET x y 后 CONFIG GET x 看是否生效；失败会明确返回错误（如 ERR Unsupported CONFIG parameter）。生产变更要写进配置文件（CONFIG REWRITE）否则重启回滚。

五、高可用与集群

Q10. Redis 集群方案应该怎么做？都有哪些方案？

方案 形态 特点
Redis Cluster（3.0+） 官方去中心化分片，16384 槽 无中心、Gossip 同步、客户端重定向（MOVED/ASK）、原生扩缩容
Codis 代理层 + 1024 预分片槽，ZK/etcd 存拓扑 客户端零改造、proxy 无状态、有 Web 运维界面；proxy 多一跳、不支持部分多 key 命令
Twemproxy 代理层，一致性哈希/取模 轻量高性能，但无自动扩缩容、无高可用，需改配置重启重分布
客户端分片 ShardedJedis / JedisCluster 无代理开销，但拓扑变更要改客户端，运维复杂
Sentinel + 主从 高可用但不分片 单点容量上限，只能垂直扩容（升配）
云托管（腾讯云/AWS ElastiCache 等） 厂商集群版 免运维、支持代理模式与直连模式，成本较高

选型：中小规模（几十 GB 内）用 主从 + Sentinel；需要水平扩展、能改造客户端用 Cluster；不想动老代码用 代理（Codis/Predixy）。

Q11. Redis 集群方案什么情况下会导致整个集群不可用？

Redis Cluster 是多数派模型，关键判定是 cluster_state：

  1. 槽未全覆盖：cluster-require-full-coverage yes（默认）时，只要有一个槽没有健康主节点，整个集群置为 fail，所有节点拒绝服务（返回 CLUSTERDOWN）。
  2. 多数 master 失效：故障转移靠 master 投票，需要超过半数 master 存活。若挂掉的 master 数 > N/2 且其从节点也没起来接管，剩余节点无法达成多数派，集群 fail。
  3. 从节点无法补位：某主挂了但从节点数据太旧（cluster-replica-validity-factor、复制断流超时）、或从节点不存在 → 该槽无主 → 结合第 1 条全集群 fail。
  4. 网络分区：分区后各侧互相 ping 不通，少数派被判定 fail；多数派继续服务，但少数派恢复后其写入的数据会被覆盖丢弃。
  5. 配置/运维事故：nodes.conf 丢失或不可写、cluster-announce-ip 配错、总线端口（port+10000）被防火墙拦、cluster-node-timeout 设太短导致误判。
  6. 迁移中断：reshard 过程节点宕机导致槽处于中间态，需手工 CLUSTER SETSLOT ... STABLE 修复。

补充：单主宕但有健康从节点时，只会有秒级不可写窗口（该槽迁移完成前客户端收到 CLUSTERDOWN/MOVED），不算全集群不可用。

Q18. 说说 Redis 哈希槽的概念？

  • 集群把 key 空间划成 16384 个槽（0–16383），每个 master 负责一段连续或离散的槽。
  • 路由：slot = CRC16(key) mod 16384，CRC16 采用 CCITT/XMODEM（多项式 0x1021）。
  • hash tag：{user1000}.name 只对 {} 内内容算 CRC16，可让相关 key 落同一槽，是多 key 操作（MGET/事务/Lua）的前提。
  • 客户端缓存”槽 → 节点”映射，收到 MOVED 更新映射，收到 ASK 做一次性重定向（迁移中）。

为什么是 16384 而不是 65536（作者 antirez 的解释）：

  1. 节点心跳包要携带槽位 bitmap：16384/8 = 2KB（还会压缩），65536 就是 8KB，Gossip 流量浪费明显。
  2. 集群 master 数量通常不超过 1000，16384 个槽足够均匀分布。
  3. 槽数少，位图小，故障检测与配置传播更快。

Q19. Redis 集群的主从复制模型是怎样的？

  • 每个 master 可挂 N 个 replica，replica 复制该 master 负责的全部槽数据（不是自己分片）。
  • replica 默认只读，加入集群时自动全量同步。
  • master 故障 → 其他 master 通过 Gossip 判定 PFail，超过 cluster-node-timeout 转 Fail → 触发故障转移：由存活 master 投票，得多数票的 replica 被提升为新 master，接管原槽位并广播新配置（epoch +1）。
  • 复制机制与单机一致：PSYNC 全量（BGSAVE → RDB → 传输 → 加载）+ 增量（repl_backlog 环形缓冲 + offset），4.0 的 PSYNC2 支持主从切换后继续增量。
  • 读扩展要客户端自己做读写分离（Cluster 不会把读自动路由到从节点，除非用 READONLY 命令显式允许从节点读）。

Q20. Redis 集群会有写操作丢失吗？为什么？

会，根因是异步复制 + 无强一致：

  1. 主写成功即返回：master 收到写命令执行完就回 OK，还没同步到 replica；此时 master 宕机 → 这条写丢失（AOF everysec 还会再丢最多 1s）。
  2. 故障转移窗口：旧 master 恢复后作为 replica 加入，会清空自己的数据以新 master 为准，它上面未同步的写被丢弃。
  3. 脑裂/网络分区：少数派 master 仍接受写入（写本地成功），分区恢复后被降级并全量同步，这些写全部丢失。
  4. epoch 冲突：旧 epoch 的写入在合并时被覆盖。

缓解手段：

  • WAIT numreplicas timeout：同步等 N 个副本确认（牺牲延迟换可靠性）。
  • min-replicas-to-write 1 + min-replicas-max-lag 10：健康副本不足时直接拒绝写，避免”写了但没人收到”。
  • appendfsync always（性能代价大）、repl-diskless-sync 降低同步窗口。
  • 业务侧：幂等设计 + 补偿对账，关键数据以 MySQL 为权威源，Redis 只做缓存/加速。

Q21. Redis 集群之间是如何复制的？

严格说是主从之间的复制（”集群间复制”通常指跨集群同步，要靠 redis-shake/redis-port 或业务双写）。复制流程：

  1. replica 配置 REPLICAOF host port（集群内由 Cluster 自动建立）。
  2. 首次/断流太久 → 全量同步：replica 发 PSYNC ? -1，master BGSAVE 生成 RDB（可用 repl-diskless-sync 直接 socket 传输），同时把新写命令写入 backlog，RDB 传完再补发增量。
  3. 之后 → 增量同步：master 把写命令同时写入 repl_backlog（环形缓冲，默认 1MB，高写入场景要调到几十 MB），replica 按 offset 拉取。
  4. PSYNC2（4.0+）：用 replid + offset 双标识，主从切换后新 master 的 replid 可继承，replica 不必全量重同步（大幅降低切换代价）。
  5. 断点续传失败（offset 已被环形缓冲覆盖）→ 退回全量。

Q22. Redis 集群最大节点个数是多少？

  • master 数量硬上限 16384（每个 master 至少要有一个槽），超过就无法分配。
  • 总节点数（含 replica）没有硬编码上限，但受 Gossip 开销、总线连接数、cluster-node-timeout 内的心跳包量、每节点内存影响，实际官方建议单集群 master ≤1000，整体几百节点量级。
  • 更大规模应拆成多集群 + 业务路由（或引入代理层聚合）。

Q23. Redis 集群如何选择数据库？

Cluster 只支持 db 0，SELECT 在集群模式下直接报错：ERR SELECT is not allowed in cluster mode。

  • 单机/主从支持 databases 16（默认），但多 db 不隔离 CPU/内存/淘汰，运维与监控都混乱。
  • 推荐统一用 key 前缀做业务隔离（如 order:、user:），这也便于按前缀做分片与治理。

Q52. Redis 集群不能使用的命令

跨槽多 key 命令（除非用 hash tag 让 key 同槽）：

  • MGET、MSET、MSETNX、DEL/EXISTS（多 key 时）
  • SUNION、SINTER、SDIFF、SINTERSTORE、SMOVE
  • ZUNIONSTORE、ZINTERSTORE、ZDIFF
  • PFMERGE、BITOP
  • RENAME、RENAMENX（要求源与目标同槽）
  • RPOPLPUSH、LMOVE、BLMOVE
  • SORT（带 BY/GET 时相关 key 必须同槽）

事务与脚本：MULTI 中所有 key 必须同槽，否则 CROSSSLOT；EVAL/EVALSHA 声明的 KEYS 必须同槽。

库/实例级：SELECT、MOVE、SWAPDB（不支持）。

管理与复制：SLAVEOF/REPLICAOF、MIGRATE（内部使用，客户端慎用）、DEBUG 部分子命令、CLUSTER MEET/FORGET 只能对特定节点执行。

只作用于单节点的命令（不是”不能用”，而是”只看到局部”）：KEYS、SCAN、DBSIZE、FLUSHDB、FLUSHALL —— 需要客户端遍历所有 master。

解决思路：hash tag 同槽、客户端聚合结果、pipeline 按节点分组（JedisCluster 自动按槽分组）、把服务端集合运算改成客户端逻辑。

Q58. Redis Cluster 集群运行 Lua 脚本会有什么问题？

  1. KEYS 必须同槽：脚本声明的所有 KEYS 要走同一槽，否则 CROSSSLOT —— 用 hash tag（{uid}:a、{uid}:b）解决。
  2. 脚本阻塞整个分片：Lua 在单线程内执行，长循环/大集合遍历会卡住该节点所有请求，必须限制循环次数与数据规模（busy-reply-threshold、lua-time-limit 只能告警不能中断）。
  3. 不能跨分片访问：脚本里只能操作本节点数据，不能读其他节点的 key。
  4. EVALSHA 的 NOSCRIPT 问题：脚本缓存是节点本地的，客户端连到不同节点可能收到 NOSCRIPT，需要 SCRIPT LOAD 到所有节点，或客户端捕获后回退 EVAL。
  5. 迁移/故障转移期间会失败：可能收到 TRYAGAIN、MOVED、ASK，客户端要带重试与重定向处理。
  6. 错误不回滚：脚本中 redis.call 报错会中断脚本，但已执行的写不会撤销（与 MULTI 类似的无回滚语义）。
  7. 7.0 的 FUNCTION 同样受槽限制，且需要 FUNCTION LOAD 到所有节点（或 FUNCTION LOAD REPLACE 配合集群同步）。

Q63. Redis 集群使用的路由函数

  • CRC16 采用 CCITT / XMODEM 变体（多项式 0x1021，初值 0），客户端与服务端保持一致（如 Jedis 的 JedisClusterCRC16.getSlot()）。
  • 带 hash tag 时只对 {} 之间的内容计算，为空则用整个 key。
  • 定位流程：本地槽缓存 → 若槽属于其他节点返回 MOVED slot host:port（永久，更新缓存重试）；迁移中返回 ASK slot host:port（临时，先 ASKING 再发命令，不更新缓存）。
  • 客户端实现：Jedis JedisClusterInfoCache 维护 slot → JedisPool，Lettuce 有 RedisClusterClient 拓扑刷新（cluster-topology-refresh）。

六、客户端与常用命令

Q14. Redis 支持的 Java 客户端都有哪些？官方推荐用哪个？

  • Jedis：直连、同步 API、贴近原生命令，连接非线程安全，必须配 JedisPool。
  • Lettuce：基于 Netty，线程安全，支持同步/异步/响应式，自动重连与拓扑刷新，Spring Boot 2.x 起默认客户端。
  • Redisson：Netty 长连接 + 分布式对象框架（见 Q15）。
  • Spring Data Redis：抽象层，底层可切 Jedis/Lettuce。

官方文档的 Java 客户端列表以 Jedis 与 Lettuce 为首推；生产新项目普遍是 Lettuce（基础缓存）+ Redisson（分布式锁/队列） 组合，老项目大量用 Jedis。

Q15. Redis 和 Redisson 有什么关系？

  • Redis 是服务端；Redisson 是 Java 客户端 + 分布式工具框架（In-Memory Data Grid），二者是”服务器 ↔ 客户端生态”的关系，Redisson 不是 Redis 的分支或发行版。
  • Redisson 在 Redis 之上封装了：分布式锁 RLock（看门狗自动续期、可重入）、分布式集合/Map/Queue/Deque、RBucket、布隆过滤器、限流器 RRateLimiter、分布式原子变量、RMapCache（带过期）、Spring Cache 集成。
  • 支持单机、主从、Sentinel、Cluster、云托管多种部署形态。

Q16. Jedis 与 Redisson 对比有什么优缺点？

维度 Jedis Redisson
定位 轻量原生命令封装 分布式对象/工具集
连接 短连接 + 连接池，非线程安全 Netty 长连接，线程安全
API 命令级（jedis.set） 面向对象（map.put）
性能 最高（封装最少） 略低（网络 + 封装 + Lua 开销）
功能 基础命令 锁、队列、限流、布隆、缓存一致性等
学习成本 低 中高，需理解其锁语义
适用 简单 KV、性能敏感、批处理 分布式协调、复杂数据结构

补充：Lettuce 是 Jedis 的现代替代（线程安全 + 异步 + 自动拓扑刷新），新项目优先 Lettuce；Redisson 的锁有 30s 看门狗续期，不要与自研 SETNX 锁混用同一 key。

Q17. Redis 如何设置密码及验证密码？

  • 配置文件：requirepass yourStrongPass；主从还要 masterauth；集群每个节点都要配。
  • 运行时：CONFIG SET requirepass xxx 后 CONFIG REWRITE 持久化。
  • 客户端认证：redis-cli -a pass --no-auth-warning，或连接后 AUTH pass；6.0 起支持 ACL：AUTH user pass、ACL SETUSER u on >pwd ~key:* +@all。
  • 安全加固：只监听内网 + 防火墙、禁用危险命令（rename-command FLUSHALL ""、rename-command KEYS ""）、开启 TLS、不要暴露 6379 到公网、定期轮换密码。

Q24. 怎么测试 Redis 的连通性？

  • redis-cli -h host -p port PING → 期望 PONG；带密码加 -a。
  • 集群：redis-cli -c -p 7000 PING，再看 CLUSTER INFO/CLUSTER NODES。
  • 端口层：telnet host port、nc -vz host port、Test-NetConnection（Windows）。
  • 延迟：redis-cli --latency、--latency-history；系统层抖动用 --intrinsic-latency 100。
  • 应用侧：连接池 pingBeforeActivateConnection、健康检查接口读 INFO server 的 redis_version。

Q25. Redis 中的管道有什么用？

  • 核心作用是减少网络往返（RTT）：N 条命令打包一次发送、一次读回，把 N 次 RTT + N 次 syscall/中断压成 1 次，批量场景吞吐可提升数倍到数十倍。
  • 典型用途：批量导入/预热、批量删除、批量查询、离线数据灌入、迁移。
  • 使用要点：单批 1000–5000 条为宜（过大占内存、阻塞服务端输出缓冲）；单条命令失败不影响其他；不保证原子性；Cluster 中要按节点/槽分组（JedisCluster 已自动分组）。
  • 与事务的区别：pipeline 只是”批量发送”，MULTI/EXEC 才是”批量原子执行”。

Q26. 怎么理解 Redis 事务？

MULTI 开启 → 命令入队返回 QUEUED → EXEC 一次性顺序执行 → DISCARD 放弃 → WATCH key 做乐观锁（EXEC 前 key 被改则整体放弃，返回 nil）。

三个关键认知：

  1. 原子性有限：EXEC 执行期间不会插入其他客户端命令，但不支持回滚。
  2. 两类错误行为不同：
    • 入队错误（命令不存在、参数个数错）→ EXEC 直接返回错误，全部不执行。
    • 运行期错误（对 String 执行 LPUSH）→ 该条失败，其余继续执行，需业务补偿。
  3. 不是关系库事务：无隔离级别、无 MVCC、无回滚，只有”批量 + 串行”。

实践：需要”判断 + 写入”的原子逻辑用 Lua 脚本（服务端整体执行，语义更可控）或 WATCH 做 CAS；分布式锁用 SET NX PX + Lua 释放。

Q27. Redis 事务相关的命令有哪几个？

  • MULTI：开启事务，进入入队模式。
  • EXEC：按序执行队列中的所有命令，返回结果数组。
  • DISCARD：清空队列并退出事务。
  • WATCH key [key ...]：监视 key，事务执行前若被修改则放弃。
  • UNWATCH：取消所有监视。

注意：WATCH 必须在 MULTI 之前；Cluster 下事务内 key 需同槽；EXEC 后再 WATCH 需重新监视。

Q28. Redis key 的过期时间和永久有效分别怎么设置？

  • 设置过期：EXPIRE/PEXPIRE（相对秒/毫秒）、EXPIREAT/PEXPIREAT（绝对时间戳）、SETEX/PSETEX、SET key val EX 10/PX 10000、GETEX（读的同时改 TTL）。
  • 设为永久：PERSIST key 移除过期；或 SET key val（注意会清掉原有 TTL，要保留用 SET ... KEEPTTL）。
  • 查询：TTL/PTTL → -1 表示永久，-2 表示 key 不存在。
  • 细节：RENAME 会继承源 key 的 TTL；EXPIRE 对不存在的 key 返回 0；从节点不主动删除过期 key，等主节点的 DEL 同步；RDB 持久化后重启，过期时间按绝对时间戳重算（不会”复活”）。

Q32. Redis 如何做大量数据插入？

推荐按效率排序：

  1. redis-cli --pipe（最快，百万级/秒）：把命令写成 RESP 协议文本，管道喂给它。
  2. 应用侧 pipeline 分批（每批 1000–5000 条），比逐条快几十倍。
  3. 临时降级持久化：导入期间 appendonly no、save ""，完成后恢复并做一次 BGSAVE。
  4. 环境优化：同机房、关 THP、避免 swap、调大 client-output-buffer-limit、确认带宽足够。
  5. Cluster：按槽把数据拆成多个文件，分别导入对应节点（redis-cli --pipe -c 不支持自动跨节点分流，需自己分组）。
  6. 导入后校验：DBSIZE、抽样 GET、INFO memory。

Q53. Redis 管道实现原理，是原子性的吗？

实现原理：

  1. 客户端把 N 条命令依次写入本地的 socket 输出缓冲（用户态），最后一次性 write 发出，而不是”发一条等一条”。
  2. 服务端事件循环一次性 read 到输入缓冲区，逐条解析、逐条执行。
  3. 所有响应先写入客户端输出缓冲，最后一次性回写给客户端。

省掉的是：N−1 次 RTT、N−1 次 write/read 系统调用（用户态↔内核态切换）、N−1 次网卡中断与软中断。所以吞吐提升主要来自网络与系统调用开销的摊薄，不减少单条命令的 CPU 开销。

不是原子性的：

  • pipeline 没有 MULTI/EXEC，服务端仍是逐条执行，其他客户端的命令可以插在中间（尤其当一批很大时）。
  • 某条命令执行失败（如类型错误）不影响后续命令，结果是”部分成功”。
  • Cluster 下 pipeline 可能跨节点，客户端要按槽/节点分组（JedisCluster 自动分组），跨节点更谈不上原子。

要原子怎么办：单条命令（SET NX PX、INCR）、MULTI/EXEC（原子执行但不回滚）、Lua 脚本（服务端整体执行，最常用）、7.0 的 FUNCTION。

七、分区与扩容

Q33. 为什么要做 Redis 分区？

  • 突破单机内存上限：单实例再大也会受 fork、持久化、故障恢复时间约束。
  • 提升吞吐与利用多核：多机多实例并行，线性扩展 QPS。
  • 降低故障影响面：单分片故障只影响部分数据（视架构）。
  • 支持业务隔离与就近部署：按业务/地域分片，独立扩缩容。

Q34. 你知道有哪些 Redis 分区实现方案？

  1. 客户端分片：范围分区（按 id 区间）、哈希取模（hash % N）、一致性哈希（带虚拟节点，扩缩容只迁移部分数据）、预分片（提前建 2^n 个实例，翻倍时成对迁移）。
  2. 代理分片：Twemproxy、Codis、Predixy、Envoy Redis Proxy —— 客户端把它当单实例，代理负责路由与聚合。
  3. 服务端路由分片：Redis Cluster（16384 槽 + Gossip + MOVED/ASK 重定向）。
  4. 云托管集群版：厂商在 Cluster 或代理之上封装（支持”代理模式/直连模式”）。

对比：客户端分片无额外跳数但运维重；代理分片兼容老代码但多一跳、有单点风险；Cluster 最完整但要客户端支持并受多 key 限制。

Q35. Redis 分区有什么缺点？

  • 多 key 操作受限：MGET、事务、Lua、集合运算要求 key 同分片（Cluster 靠 hash tag）。
  • 扩缩容要迁移数据，有 rehash 成本与线上风险（大 key 迁移尤其慢）。
  • 数据倾斜：热点 key 集中在一个分片，扩容也救不了（要靠 key 打散/本地缓存）。
  • 运维复杂度上升：多实例监控、配置一致性、升级灰度、故障定位链路变长。
  • 聚合统计困难：DBSIZE、KEYS、全量扫描需遍历所有节点，报表要客户端/离线汇总。
  • 一致性与故障语义更复杂：分片级 failover、跨分片无原子性。
  • 客户端需感知拓扑（或引入代理，多一跳延迟与单点风险）。

Q36. Redis 持久化数据和缓存怎么做扩容？

缓存扩容（允许重建）

  1. 加节点 → 一致性哈希或 Cluster reshard 迁移槽 → 灰度切流 → 按历史热 key 预热（TTL 打散）。
  2. 过渡期双读（新老集群都查）或短暂双写，避免冷启动把 DB 打穿。
  3. 观察命中率与 DB 负载再摘除老节点。

持久化数据扩容（不能丢）

  1. Cluster 在线扩：redis-cli --cluster add-node 加节点 → --cluster reshard 按槽 MIGRATE 搬数据（可限速 --cluster-pipeline、分批、错峰）；期间槽处于 migrating 态，客户端靠 ASK 重定向。
  2. 单机/主从升级：先加从节点扩读 → 用 redis-shake / redis-port 做全量 + 增量在线迁移 → 校验后切流。
  3. 停机窗口方案：BGSAVE → 拷 RDB 到新实例加载 → 补齐增量（AOF 或业务补偿），速度快但有停机。
  4. 预分片思想：提前规划 2^n 个实例，容量翻倍只需成对迁移一半数据。
  5. 迁移期要点：限速、避开高峰、监控迁移进度与延迟、客户端带重试与重定向处理、迁移后校验 key 数与抽样数据。

Q37. 分布式 Redis 是前期做还是后期规模上来了再做好？为什么？

结论：架构上提前预留，实现上按需分片。

理由：

  • 前期不做分片的收益：单实例足以支撑 10 万 QPS、几十 GB，复杂度和运维成本最低，还能用多 key 操作、事务、Lua 全功能。
  • 前期必须预留的能力：
    1. key 设计规范（统一前缀、可加 hash tag，便于日后同槽）；
    2. 禁止大 key、控制单 key 规模；
    3. 客户端统一封装（RedisService 抽象），从单机切 Cluster 时只改一层；
    4. 容量/QPS/内存/命中率有监控与阈值告警。
  • 后期才分片的代价：改造客户端、迁移数据、重写多 key 逻辑、灰度风险，成本远高于前期设计。
  • 触发条件：内存超单机 60–70%、QPS 接近单实例上限、需要多活/容灾、单实例 fork 恢复时间不可接受。
  • 演进路径：单机 → 主从 + Sentinel → Cluster（或代理分片），逐步演进而不是一步到位。

Q38. Twemproxy 是什么？

Twitter 2012 年开源的 Redis/Memcached 代理（C 编写，单线程 + 多路复用）：

  • 支持一致性哈希（ketama）、取模、随机等分片算法。
  • 客户端当单实例用，减少后端连接数，协议解析开销小（性能损耗通常 <10%）。
  • 缺点：不支持动态扩缩容（改配置重启会重分布数据）、不支持多 key 跨节点操作、不支持 Cluster 命令与事务跨节点、自身是单点（需前面再挂 LB）、项目活跃度低。
  • 现多被 Codis / Predixy / Envoy 或原生 Cluster 取代。

Q39. 支持一致性哈希的客户端有哪些？

  • Jedis 的 ShardedJedis：内置一致性哈希 + 虚拟节点（TreeMap + MD5 哈希），是最经典的客户端分片实现。
  • Twemproxy：代理层实现 ketama 一致性哈希。
  • 其他语言生态：redis-rb 的 Redis::Distributed、部分 .NET/Node 客户端自带一致性哈希分片。
  • 需要区分：Codis 用的是预分片槽（1024 slots）而非一致性哈希，常被混淆；Cluster 用的是 16384 槽 + CRC16，也不是一致性哈希。

八、性能与优化

Q45. Redis 是单线程的，如何提高多核 CPU 的利用率？

  1. 单机多实例（最有效）：一台机器起多个 Redis 进程（不同端口/独立配置），taskset/numactl 绑核，让每个实例吃一个物理核，避免跨 NUMA 访问。
  2. 分片：把数据与请求分散到多台机器/多个实例。
  3. 6.0 的 I/O 多线程：io-threads 4 让多线程承担 socket 读写与协议解析（命令执行与数据访问仍是单线程，所以无锁），只对网络瓶颈场景有效。
  4. 后台线程（bio）：AOF fsync、lazyfree、关闭大文件等已放后台，不占主线程。
  5. 读写分离：从节点分担读流量（客户端或用代理路由）。
  6. 客户端侧并发：多连接 + pipeline 提升单实例吞吐（利用的是网络而非多核）。
  7. 避免阻塞：禁 KEYS、大 SMEMBERS、大 key DEL，减少单核长时间占用。

Q51. Redis 为什么快？（含线程切换、带宽瓶颈、网络耗时）

五个主因：

  1. 纯内存操作：读写 ~100ns 级，避免任何磁盘 I/O。
  2. 单线程：无锁、无竞争、无上下文切换，CPU 缓存亲和性好。
  3. I/O 多路复用：epoll 事件驱动 + 非阻塞 socket，少量线程管理海量连接。
  4. 高效数据结构：SDS、dict + 渐进式 rehash、跳表、listpack、jemalloc 减少分配开销。
  5. 协议与命令简单：RESP 易解析，命令多为 O(1)/O(logN)，无复杂查询。

线程切换为何费时：
需要保存/恢复寄存器与栈指针、陷入内核调度、切换后 L1/L2 缓存与 TLB 失效（一次 cache miss 上百周期）、多核间要走缓存一致性协议（MESI）同步，还有调度器本身的开销。一次切换约 1–10μs，在高频短任务场景下，切换开销可能超过实际计算，所以单线程反而是优势（Redis 只在必要时用多线程做 I/O）。

带宽是不是瓶颈：

  • 千兆网卡理论上限 125MB/s，万兆 1.25GB/s。
  • 普通命令请求/响应约 100B 量级，10 万 QPS 也只用到 ~10MB/s，远未打满 → 小命令场景瓶颈在 CPU/延迟，不在带宽。
  • 但大 value（1MB）、MGET 大批量、全量同步会瞬间打满网卡；另外网卡中断/软中断通常集中在一个核（RSS 多队列、irqbalance 可缓解），高 PPS 时软中断本身就会成为瓶颈。

网络传输中哪里耗时：
客户端序列化 → 系统调用（用户态↔内核态两次拷贝）→ TCP 分段/拥塞控制/重传 → 网卡 DMA → 交换机/路由 → 对端网卡中断 + 软中断 → 内核缓冲拷贝到用户态 → 协议解析 → 反序列化。
其中 RTT 是大头：同机房 0.1–0.3ms，跨城 10–30ms，跨国 100ms+。pipeline 把多次 RTT 压成一次，是降低网络耗时最直接的手段；同时减少 syscall 与中断次数，吞吐提升明显。

Q54. Redis 大 key 问题评估及处理

评估标准（业界经验值，按业务调整）：

  • String：>10KB 需关注，>1MB 视为大 key。
  • 容器类（Hash/List/Set/ZSet）：元素数 >5000–10000，或总内存 >1MB。
  • 复合判断：单 key 占实例内存比例 >1%，或 MEMORY USAGE 结果异常。

危害：

  • 单线程阻塞：DEL/过期/序列化/RDB 保存都会卡住全站。
  • 网络拥塞：MGET 一次拉几百 MB，打满带宽并撑爆客户端内存。
  • 内存倾斜：分片间不均衡，扩容无效。
  • 迁移慢：MIGRATE 大 key 会长时间阻塞。
  • fork COW 放大：大 key 被修改会复制整页。

检测：

  • redis-cli --bigkeys（抽样按类型统计最大，轻量）
  • MEMORY USAGE key（单 key 精确）
  • SCAN + STRLEN/LLEN/HLEN/ZCARD/SCARD
  • 离线分析 RDB：rdbtools、redis-rdb-cli（最全）
  • MONITOR 采样、SLOWLOG 定位、云厂商的大 key 分析工具

处理：

  • 拆分：String 按后缀分片；Hash 按 id 取模分桶（hash:{id%16}）；List/ZSet 按时间或序号分段。
  • 压缩：value 用 protobuf/snappy/gzip。
  • 只取所需：HMGET 指定字段，避免 HGETALL；分页 HSCAN/SSCAN/ZSCAN。
  • 删除：UNLINK + lazyfree-lazy-*，或 HSCAN 批量 HDEL 渐进清理。
  • 预防：设计规范 + 代码评审 + 监控告警（定时 --bigkeys）。

Q55. Redis 多路复用和单线程

机制：事件循环在 ae.c 里按平台选 epoll（Linux）/kqueue（BSD）/evport（Solaris）/select（兜底）。单线程把所有 client fd 注册读事件，事件就绪后回调：accept → 读命令 → 执行 → 写回包。socket 全非阻塞，单个慢连接不会卡死全局。

为什么单线程还能高并发：

  • 连接虽多但多数空闲，事件驱动只处理活跃 fd，不需要”一连接一线程”。
  • 命令是内存操作（μs 级），CPU 不是瓶颈，瓶颈在网络与 RTT。
  • 单线程避免锁与上下文切换，延迟更稳定、可预测。

局限：任何一条慢命令（KEYS、大 ZRANGE、复杂 Lua、大 key 删除）都会阻塞全部请求；无法利用多核。

弥补：多实例分片、6.0 的 io-threads（多线程只做 socket 读写与协议解析，命令执行仍单线程，因此无锁）、后台 bio 线程处理 fsync/lazyfree。

Q60. Redis 响应变慢了，怎么排查？

按层次收敛，从外到内：

  1. 客户端层：RT 分布（P99/P999）、超时率、连接池是否耗尽、是否有大批次 MGET/大 key 拉取、DNS 解析、是否跨机房。
  2. Redis 内部：
    • SLOWLOG GET 10 看慢命令与耗时分布
    • INFO commandstats（usec_per_call 找异常命令）
    • LATENCY DOCTOR / LATENCY HISTORY event
    • redis-cli --latency、--latency-history（看是否周期性尖刺）
    • --intrinsic-latency 100（区分”Redis 慢”还是”机器/虚机被抢占”）
    • --bigkeys、--hotkeys（大 key/热 key）
  3. 系统层：top -H 看是否单核 100%、vmstat/sar 看 swap 与上下文切换、iostat 看磁盘（AOF fsync / RDB 落盘）、netstat -s 看重传与丢包、mtr 看链路、THP 是否开启。
  4. 常见根因：大 key、热 key、KEYS/大集合命令、fork（BGSAVE/AOF 重写）导致的延迟尖刺、AOF everysec fsync 抖动、swap、内存碎片、连接突增、输出缓冲爆、集群 reshard/重定向、从节点全量同步、Lua 长脚本。
  5. 处置：禁用或替换阻塞命令、拆大 key、持久化错峰、限流降级、扩分片/加从节点、升级版本、调 hz/io-threads/maxmemory-samples。

九、业务实战

Q61. Redis 统计网站的 UV 和 PV

PV（访问量）：

  • INCR pv:20261124，按页面用 HINCRBY pv:20261124 /page 1（一次写少 key，避免热点）。
  • 超高并发时本地聚合（每 N 秒批量 INCRBY）+ 按小时分 key 防单 key 过热。

UV（独立访客）三方案：

方案 内存 精度 说明
Set 每用户 ~50B+ 精确 只适合小规模（万级以内），支持查成员
Bitmap 用户 id 连续整型时 1 亿用户 = 12.5MB/天 精确 SETBIT/BITCOUNT，支持多日留存位运算（AND=留存、OR=周活）
HyperLogLog 12KB/键，误差 0.81% 估算 PFADD/PFCOUNT，PFMERGE 可小时→天→周合并，海量场景首选

组合实践：

  • 日活/月活用 HLL 估算（成本极低、可合并）；对账/结算类指标用 Bitmap 精确。
  • 按时间分 key（uv:20261124:10 每小时一个），读取时 PFMERGE 或位运算合并。
  • 若用户 id 稀疏（几十亿且不连续），先用哈希映射压缩 id 再置位。
  • 所有统计 key 设 TTL（如 35 天），避免无限堆积。
  • 漏斗、留存、复访用 Bitmap 位运算，比 HLL 更灵活（HLL 只能计数，不能查具体用户）。

Q62. 微信运动每天晚上十点”占领了多少个朋友的榜首”功能实现（海量数据）

问题本质：每天 22:00 前，对每个用户 u 计算”好友中步数低于 u 的人数 N”，并推送。规模：十亿级用户 × 平均上百好友 = 千亿级边，而且要在很短时间内算完并推送。

关键判断：

  • 不能”用户打开时遍历好友实时算”——N×M 次比较，单用户上千好友时也很慢。
  • 不能”给每个用户建一个好友步数 ZSet”——内存 O(边数)，千亿级完全不可行。
  • 必须离线分布式批处理 + 结果缓存。

实现方案：

  1. 数据上报：手机端定时/批量上报步数，接入层用 Redis 按 uid % 1024 分片做当日缓冲与去重（Hash 或 Stream），再异步落 Hive/数仓；做好作弊步数过滤（上限、跳变检测）。
  2. 离线计算（Spark/MapReduce）：
    • 好友关系表按 owner 用户分区（(u, f) 按 hash(u) 打散），步数作为较小的一侧做分桶 join（不是无脑广播全量）。
    • 对每条边比较 step(f) < step(u)，输出 (u, 1)，按 u 聚合 sum 得到 N。
    • 优化：超大 V 用户（好友上千）单独任务；按步数分桶排序减少比较；只对”当日有步数”的用户计算，离线用户沿用上次或跳过。
  3. 调度：步数在 22:00 前基本稳定 → 提前跑批（如 20:30 起），先算活跃用户，冷用户按需/次日补算；结果分片写入 KV，key 带日期（occupy:{uid}:20261124），TTL 2 天。
  4. 推送：推送服务按分片限速拉取结果，打散到 21:50–22:30 的时间窗，避免 22:00 瞬时洪峰；失败重试 + 幂等（同一天只推一次）。
  5. Redis 承担的角色：步数上报缓冲与去重（分片 Hash/Stream）、活跃用户当日榜单（ZSet，仅对活跃子集建，避免全量）、结果缓存与热点读取、限流与幂等标记。
  6. 工程细节：好友关系图分库分表、跨天/时区边界、灰度开关与降级（算不完时只对活跃用户出结果）、监控算力与延迟、作弊用户降权、隐私合规（只输出”人数”，不暴露具体好友步数）。

附：几条高频”一句话结论”

  • 快的原因：内存 + 单线程无锁 + epoll + 高效结构 + 简单协议。
  • 集群多数派：半数以上 master 存活才能故障转移；require-full-coverage 下缺槽即全站不可用。
  • 一致性：异步复制，Redis 不是强一致系统，关键数据以 DB 为准。
  • 大 key 是万恶之源：阻塞、带宽、倾斜、COW、迁移，一个都跑不掉。
  • 分片前提：key 可加 hash tag、客户端有抽象层、能接受多 key 限制。
  • 容量红线：maxmemory 取物理内存 60%–70%，单实例内存控制在 10–20GB 更稳。
