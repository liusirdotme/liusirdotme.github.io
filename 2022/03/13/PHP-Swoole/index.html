Swoole

一、基础

      Swoole就是披着PHP外衣的C程序，类似于Java等语言里面的高阶功能，如持久连接、异步通信、Websocket、多线程等。

      Swoole是由C语言开发的PHP扩展类，由于有着C语言的优势，Swoole在内存管理、数据结构、通信协议解析等方面优势明显。它是一个面向生产环境的PHP异步网络通信引擎，使PHP开发人员可以编写高性能的异步并发TCP、UDP、Unix Socket、HTTP、WebSocket等服务。Swoole可以广泛应用于互联网、移动通信、企业软件、云计算、网络游戏、物联网（IOT）、车联网、智能家居等领域。

二、实战

  1. 安装

    • 下载源码包至/usr/local/src目录下
    • 解压 sudo tar -zxvf swoole-4.4.3.tgz
    • 切换目录 cd swoole-4.4.3
    • 运行sudo /usr/local/php/7.3/bin/phpize命令，生成configure可执行文件
    • 运行配置sudo ./configure --with-php-config=/usr/local/php/7.3/bin/php-config
    • 安装扩展sudo make && sudo make install
      • 报错：configure: error: C compiler cannot create executables，解决sudo xcodebuild -license accept
    • 修改php.ini文件，增加extension=/path/swoole.so
    • 重启php-fpm
    • 查看是否安装成功php7.3 -m，显示swoole则成功

Swoole版本对比

一、版本总览表

版本 最低 PHP 核心定位 重大特性 破坏性变更 适用场景
Swoole 1.x PHP5.3~7.0 异步回调时代 基础 Server(TCP/HTTP/WebSocket)、异步回调、Task、Timer、Table 无协程，全回调编程 老项目、传统异步服务，现已淘汰
Swoole 2.x PHP7.0+ 协程诞生 引入 C 栈协程，go() 关键字，协程 TCP 客户端 协程仅客户端，Server 还是回调；API 不稳定 早期协程尝鲜，不推荐生产
Swoole 4.x PHP7.1~8.1 协程黄金版（生产最广泛） 1. 全协程 Server：Http/Http2/WebSocket/TCP 都支持协程
2. 一键协程化 Swoole\Runtime::enableCoroutine()
3. 协程 MySQL/Redis/PostgreSQL 客户端、协程文件、协程 DNS
4. ProcessPool、多 Reactor 线程、max_concurrency、协程取消 Co::cancel
5. Swoole\Table 增强		 4.0 起不再支持 PHP5；4.7 Table 不再支持数组式访问 $table[$key] Hyperf、EasySwoole 等主流框架；绝大多数线上业务，存量主力
Swoole 5.x PHP8.1+ 精简重构版 1. 强类型声明，全 API 参数返回值类型
2. swoole-cli 独立二进制（无需系统 PHP）
3. 协程性能优化、内存优化
4. 支持 io_uring		 重大移除：删除内置协程 MySQL/Redis/PostgreSQL 客户端，不再维护；废弃大量旧 API；移除旧异步回调客户端；不再支持 PHP7 新项目，愿意使用原生 PDO/Redis 扩展 + Runtime 协程化；需要独立 swoole-cli
Swoole 6.x PHP8.2~8.4 现代化新版本 1. 原生 Fiber 支持（PHP8.1+ zend fiber）
2. io_uring 成熟、多线程池重构
3. 完善协程调试、异常链路优化
4. 更好 PHP8 新特性兼容		 继续清理遗留旧 API，逐步弱化 C 栈协程，主推 PHP Fiber 新项目、追求 PHP 原生特性、io_uring 高性能场景

二、分版本详细核心升级 & 区别

✅ Swoole 1.x（回调时代，古董）

  • 编程模型：事件回调，没有协程，写代码是 onReceive/onRequest 回调，遇到 IO 必须异步非阻塞。
  • 能力：TCP/UDP/HTTP/WebSocket 服务器、Task 异步任务、毫秒定时器、Swoole\Table 共享内存。
  • 痛点：回调地狱，代码难维护；阻塞 IO 直接卡死 Reactor；PHP 版本老旧。

一句话：没有协程的 Swoole，现在几乎没人用。

✅ Swoole 2.x：协程初试

  • 里程碑：首次引入协程（ucontext C 栈协程），go(function(){})。
  • 限制：Server 本身仍然是回调模式，协程只可以在回调内部创建，只能用协程 TCP 客户端；没有一键协程化。
  • 坑：协程生态不全，不稳定，很多阻塞函数无法挂起。

一句话：协程客户端可用，Server 不能全协程，属于过渡版本。

✅ Swoole 4.x（最重要，生产首选）

分水岭版本，PHP 协程生态成熟，Hyperf、EasySwoole、Mix 所有主流 Swoole 框架基于 4.4~4.8

  1. 全协程服务器：HttpServer 可以直接在 onRequest 里写同步风格代码，底层自动协程调度，告别回调地狱。
  2. Runtime 一键协程化 Swoole\Runtime::enableCoroutine()：原生 file_get_contents、PDO、mysqli、stream 全部自动变成协程非阻塞，不用改业务代码。
  3. 内置全套协程客户端：Swoole\Coroutine\MySQL / Redis / PostgreSQL，高性能。
  4. 新组件：ProcessPool、连接池配套能力、Http2、WebSocket 协程、协程 DNS、协程文件读写。
  5. 4.7 关键变更：Swoole\Table 不能再用数组写法 $table['key']，只能用 get/set；新增 Co::cancel() 协程取消。
  6. 4.8：SSL 握手协程化，解决 TLS 握手阻塞 Reactor 问题。

4.x 内部小版本差异

  • 4.0：协程 HttpServer 正式稳定
  • 4.4：Runtime 一键协程化稳定，Hyperf 起点版本
  • 4.6：支持 PHP8
  • 4.7：Table 数组访问废弃、协程取消
  • 4.8：TLS 协程化、大量稳定性修复，4.8 是 4.x 系列最终稳定推荐版

一句话：4.x = 协程能力最强、生态最完善、文档/案例最多；缺点：内置协程客户端在 5.0 被砍掉。

✅ Swoole 5.x：破坏性精简重构

设计理念：不再维护自研数据库协程客户端，交给 PHP 原生扩展 + Runtime 协程化

  1. 移除：Swoole\Coroutine\MySQL、Redis、PostgreSQL 内置协程客户端（重大 break change！）

    业务改用原生 pdo/redis 扩展 + Runtime 自动协程化

  2. 强类型：所有 API 增加严格参数/返回值类型，PHP8 强类型体系对齐
  3. swoole-cli：独立静态二进制，打包 PHP+Swoole，不依赖宿主机 PHP 环境，部署很方便
  4. 内核优化：内存泄漏修复、协程栈优化、支持 io_uring
  5. 最低 PHP 8.1，彻底砍掉 PHP7 支持

升级大坑：4.x 业务如果大量直接使用 Coroutine\Redis/MySQL，迁移 5.x 必须改代码，重写连接池。

✅ Swoole 6.x：Fiber 时代

  1. 支持 PHP 原生 Zend Fiber 作为协程后端（替代老的 ucontext C 栈协程），可以自由切换协程实现。
  2. io_uring 成熟，提升高并发 IO 性能。
  3. 协程调试、异常栈、Xdebug 支持大幅改善。
  4. 持续清理遗留废弃 API，进一步简化内核。

三、重要分支说明：OpenSwoole（原 Swoole fork）

很多人会搞混：OpenSwoole 是社区 fork，版本号独立（22/24/26），不是 swoole-src 原版。

  • 原版 Swoole：swoole/swoole-src，版本 1/2/4/5/6，swoole PECL 包
  • OpenSwoole：openswoole/openswoole，版本 22+，pecl 包名叫 openswoole，命名空间 OpenSwoole\
  • 两者 API 大体相似，但内核、废弃策略、PHP 支持不一样，不要混用。

四、选型建议（生产环境）

  1. 老项目 / Hyperf、EasySwoole 存量：Swoole 4.8，生态成熟稳定，不轻易升 5
  2. 新项目，PHP8.1+，不想依赖 swoole 内置数据库客户端：Swoole 5.x
  3. 追求 PHP 原生 Fiber、io_uring、最新 PHP8.3/8.4：Swoole 6.x
  4. 新项目尽量不要用 OpenSwoole，除非明确需要它的特殊特性，生态资料少

五、核心差异一句话总结

  • 1.x：只有异步回调，无协程
  • 2.x：协程来了，但只有客户端协程，Server 还是回调
  • 4.x：协程黄金时代，全协程 Server + 内置全套协程数据库客户端 + Runtime 一键协程化，框架生态爆发
  • 5.x：砍掉内置数据库协程客户端，拥抱原生 PHP 扩展，强类型，swoole-cli
  • 6.x：支持 PHP 原生 Fiber，io_uring，逐步淘汰旧 C 栈协程

PHP之Swoole和Go对比

学习路径

  • 从 PHP → Swoole：你的业务代码、Composer 生态、Laravel 经验全部复用，两周能开始产出。
  • 从 PHP → Go：3–6 个月沉没成本，而且你得同时重学类型系统、错误处理（Go 没有异常，只有 error 返回值，这个思维转换对 PHP 程序员是最难的一关）、构建工具链。​你沉淀了多年的中控系统业务知识（代理账号、余额划拨、快手平台对接）全部无法迁移。
  • 从 Swoole → Go：一周。因为 Reactor、协程调度器、Channel、多进程模型这套东西是共享的，Swoole 6.x 的协程 API 和 Go 的 goroutine + channel 在心智模型上是同一套，只是语法糖不同。

Swoole有而Go给不了的东西：Swoole\Process多进程模型+Swoole\Table跨进程共享内存。

  • Go 的 goroutine 是单线程内的协程，要跨线程共享状态你得自己用 sync.Map 加锁，或者引入 etcd / Redis 做外部状态。
  • Swoole 的 Table 是零锁、跨进程、内核内存映射的，用起来就是像操作数组一样简单。
