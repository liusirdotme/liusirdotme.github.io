一、基础理论与语言

1.1 语言机制

  1. 解释型语言和编译型语言

    • 编译型语言：使用专门的编译器，针对特定的平台，将高级语言源代码一次性的编译成可被该平台硬件执行的机器码，并包装成该平台所能识别的可执行性程序的格式。

    • 在程序执行之前，需要一个专门的编译过程，把源代码编译成机器语言的文件，如 exe 格式的文件。以后要再运行时直接使用编译结果即可，如直接运行 exe 文件。因为只需编译一次，以后运行时不需要编译，所以编译型语言执行效率高。

    • 总结

      • 一次性的编译成平台相关的机器语言文件，运行时脱离开发环境，运行效率高
      • 与特定平台相关，一般无法移植到其他平台
      • Go、C、C++、Objective 等属于编译型语言

    • 解释型语言：使用专门的解释器对高级语言源代码逐行解释成特定平台的机器码并立即执行。

    • 不需要事先编译，其直接将源代码解释成机器码并立即执行，所以只要某一平台提供了相应的解释器即可运行该程序。

    • 总结：

      • 解释型语言每次运行都需要将源代码解释成机器码并执行，效率较低；
      • 只要平台提供相应的解释器，就可以运行源代码，所以可以方便源程序移植；
      • C#、PHP、Python 等属于解释型语言。

      Java 是个特例，它需要编译，但是却没有直接编译为机器语言，而是编译为字节码，然后在 Java 虚拟机上以解释方式执行字节码。

  2. 指针和引用

    • 有些语言有”指针”的概念，比如 C 语言；有些语言没有指针，取而代之的是”引用”，比如 Java、PHP。不管是”指针”还是”引用”，实际上它们的意思都是一样的，都是存储所指对象的内存地址。
    • 将某个变量赋值给指针，实际上就是将这个变量的地址赋值给指针。或者反过来说，指针中存储了这个变量的内存地址，指向了这个变量，通过指针就能找到这个变量。
    • 在编写链表代码的时候经常会有这样的代码：p->next=q，这行代码是说 p 结点中的 next 指针存储了 q 结点的内存地址。
    • 编写链表代码更复杂的经常会用到的：p->next=p->next->next，这行代码表示 p 结点的 next 指针存储了 p 结点的下下一个结点的内存地址。

  3. PHP：静态方法与 $this

    • php 中，静态方法随着类的加载而加载，优先于对象而存在。this 代表的是对象的引用，即为当前对象，静态方法是通过类调用的方法，不需要实例化，既然不需要实例化，就没有当前对象，既然没有当前对象，就不会有 this。

2.4 网站无法访问的排查路径

  1. 先判断是局部还是全局：换网络、换设备、用第三方拨测工具（如站长工具）测试。
  2. 域名解析：nslookup / dig 看是否解析到正确 IP，有无被污染或未备案导致解析被停。
  3. 运营商链路：ping、traceroute 看丢包与在哪一跳断。
  4. 端口与防火墙：telnet ip 端口 看端口是否通，云服务器检查安全组。
  5. 服务进程：ps -ef、netstat -tlnp 看进程是否存活、端口是否监听。
  6. Web 服务与后端：看 nginx 错误日志、后端应用日志，是否是 502/504。
  7. 资源层：数据库/Redis 是否连不上导致响应超时；磁盘是否写满。
  8. SSL 证书：是否过期、证书链是否完整。
  9. CDN 层：CDN 回源是否正常、缓存是否命中问题内容。

2.5 C10K 问题

  • c10k 问题是同时处理大量客户端请求的网络 sockets 优化问题。c10k 用来命名并发处理 10k 连接的问题。人们一直研究 socket 服务优化，这其中有大量因素需要考虑来允许服务器支持大量服务端。这需要结合操作系统和 web 服务器软件的限制。根据服务的可提供范围以及操作系统和硬件限制如多进程能力，多线程模型或者单线程模型可以优先考虑。与此同时需要考虑内存管理（通常依赖操作系统），这些策略隐含了 I/O 管理的各个方面。
  • 参考
    • C10K
    • C10K 中文翻译
    • C10K 中文翻译
模型 一个连接的成本 并发量级 代表实现
一个进程一个连接 进程栈 + 上下文切换开销大 百级 早期 Apache prefork
一个线程一个连接 线程栈约 1MB 千级 Apache worker、Tomcat BIO
IO 多路复用 + 事件循环 一个连接仅少量内存 万级（C10K） nginx、Redis、Node.js、Swoole
协程 用户态调度，栈 KB 级 十万级（C100K） Go goroutine、Swoole 协程、Java 虚拟线程

核心结论：瓶颈不在 CPU 而在「每连接的内存开销 + 上下文切换」，解决思路是用 epoll/kqueue 事件驱动 + 非阻塞 IO，把”等 IO”这件事从”占着线程等”变成”注册回调”。

3.1 缓存兜底方案

问题 现象 应对手段
缓存穿透 查询不存在的数据，请求每次都打到 DB 缓存空值（设短过期时间）、布隆过滤器拦截、参数合法性校验
缓存击穿 热点 key 过期瞬间，大量请求同时压到 DB 互斥锁/分布式锁重建缓存、逻辑过期不删 key、热点数据不过期
缓存雪崩 大批 key 同时过期，或 Redis 整体挂掉 过期时间加随机值打散、多级缓存、熔断降级、集群高可用
缓存与 DB 一致性 双写导致脏数据 Cache Aside（先更新 DB 再删缓存）、延迟双删、订阅 binlog 异步刷新
Redis 不可用 全部请求落到 DB，DB 被打挂 本地缓存兜底、限流、快速失败并返回降级数据

3.2 防止重复提交的几种做法

方案 实现 适用
前端禁用按钮 提交后置灰，配合 loading 只防手抖，不防绕过
Token 机制 进页面发一次性 token，提交时校验并删除（Redis DEL 返回 1 才放行） 通用表单提交
Redis 分布式锁 SET key value NX PX 3000，拿到锁才处理业务 接口级防重
唯一索引 DB 建唯一约束，重复插入直接报错 数据层面的最终兜底
幂等设计 用业务单号做幂等键，重复请求直接返回上次结果 支付、下单等强一致场景

SETNX + 过期时间必须用一条命令（SET k v NX PX n），否则”设置锁”和”设置过期”之间宕机会造成死锁。

关注点 说明
解耦 生产者只投递，不关心消费者有几个、是谁

3.4 算法题

  1. 两个大数相加 —— 字符串模拟竖式加法，从低位向高位逐位相加并处理进位，时间复杂度 O(max(m,n))。原文

  2. 大文件小内存排序 —— 典型场景：一个 10GB 的文件，内存只有 1GB，要排序。

方案 做法 复杂度 适用
外部排序（归并） 分块读到内存（如每次 100MB），块内快排后写回磁盘形成若干有序小文件；再对这些文件做 k 路归并输出 O(n log n) 全量有序输出（通用解）
分桶 / 哈希分片 先按哈希把数据散成 N 个小文件（同一 key 落到同一文件），再逐个文件在内存里排序 O(n) 均摊 找 Top K、找重复元素，不需要全量有序
位图 / 布隆过滤 只记录”是否存在”，用 bit 数组 O(n) 40 亿整数判存在性，空间可压到 512MB
小顶堆 维护大小为 K 的堆，扫描一遍 O(n log K) 只求 Top K，内存 O(K)
  1. 一秒内可以执行多少次 for 循环
语言/场景 量级 说明
C / C++ 空循环 约 1×10⁸ ~ 1×10⁹ 次 取决于 CPU 主频、是否被编译器优化掉、循环体是否有内存访问
Java 空循环（JIT 预热后） 约 1×10⁸ ~ 5×10⁸ 次 受 JIT 优化与逃逸分析影响很大
PHP 空循环 约 1×10⁷ ~ 5×10⁷ 次 解释执行，每次循环都有 opcode 派发开销
Python 空循环 约 3×10⁷ 次 CPython 解释器开销大，同样逻辑用 numpy/列表推导可快一个数量级
JS（V8）空循环 约 1×10⁸ ~ 5×10⁸ 次 JIT 优化后接近 Java
  • 实测要点：这个数字几乎没有意义——实际耗时由循环体决定。循环体内有一次内存访问，性能就可能降一个数量级；有系统调用或 IO，再降几个数量级。
  • 正确做法是关心常数因子：减少循环内的方法调用、避免重复计算长度、把循环内不变的计算提到循环外、用局部变量缓存全局变量。

4.3 中间件

  • 中间件是一种独立的系统软件或服务程序，分布式应用软件借助这种软件在不同的技术之间共享资源。中间件位于客户机 / 服务器的操作系统之上，管理计算机资源和网络通讯。是连接两个独立应用程序或独立系统的软件。相连接的系统，即使它们具有不同的接口，但通过中间件相互之间仍能交换信息。执行中间件的一个关键途径是信息传递。通过中间件，应用程序可以工作于多平台或 OS 环境。
类型 作用 典型产品
终端仿真 / 屏幕转换中间件 屏蔽不同终端的差异，统一接入 Telnet 网关、终端模拟器
远程过程调用中间件 让跨进程/跨机器的调用像本地调用 Dubbo、gRPC、Thrift、Feign
数据库中间件 分库分表、读写分离、连接池 ShardingSphere、MyCat、ProxySQL
消息中间件 异步解耦、削峰、最终一致 RabbitMQ、Kafka、RocketMQ、Pulsar
交易中间件 保障分布式事务的一致性 Tuxedo、Seata、XA
对象中间件 跨语言的对象请求代理 CORBA、DCOM

4.4 中台

  • 定义：中台是把各业务线重复建设的能力抽取、沉淀、标准化后，以「共享服务中心」的形式对外提供，让前台能快速复用而不是每次从零搭。核心是能力的复用与高效响应，而不是简单的技术分层。
  • 与平台的区别：平台是纵向的技术支撑（如数据平台、监控平台），中台是横向的业务能力沉淀，必须能被多个前台业务复用。
中台类型 沉淀的能力 典型内容
业务中台 可复用的业务能力 用户中心、订单中心、商品中心、支付中心、权限中心
数据中台 数据的采集、治理与对外服务 数据仓库、指标口径统一、标签体系、数据 API
技术中台 通用技术能力 微服务框架、消息队列、缓存、网关、CI/CD
组织中台 组织与协同机制 共享服务中心的团队划分与考核机制

风险提示：中台不是万能药。业务差异大、迭代速度要求极高的团队强上中台，很容易变成”中台响应慢、前台绕开走”的局面。判断标准是能力是否真的在多条业务线被重复建设。

4.5 数据埋点

  • 埋点分析，是网站分析的一种常用的数据采集方法，是数据采集领域（尤其是用户行为数据采集领域）的术语，指的是针对特定用户行为或事件进行捕获、处理和发送的相关技术及其实施过程，如用户某个 icon 点击次数、观看某个视频的时长等。
  • 埋点的作用就是用来做用户动作行为分析的，即时有效的埋点可以为产品的下一步推广、实施、改进等做导向。

埋点方式对比：

方式 实现 优点 缺点
代码埋点（初级） 在业务代码中显式调用上报 SDK 数据精准、可带丰富业务参数 侵入性强、改动需发版、漏埋/错埋难发现
可视化埋点（中级） 运营在页面上圈选元素，自动生成采集规则 无需开发介入、上线快 只能采通用事件（点击/曝光），复杂逻辑采不到
全埋点 / 无埋点（高级） SDK 自动采集所有点击、页面浏览等事件 零侵入、可回溯补分析 数据量大、缺乏业务语义、需大量后端清洗

埋点规范要点：事件命名统一（模块_动作_对象）、参数口径统一且在数据字典中登记、区分「事件发生时间」与「上报时间」、带上用户标识与设备标识、做好版本号与渠道号，便于后续归因。

5.1 优化网站速度

  • 总的方向：减少请求数、减少资源大小、找最快的服务器。
优化方向 具体手段 效果说明
减少请求数 合并 CSS/JS、CSS Sprite、内联小图标（base64） HTTP/1.1 下并发受限，请求数直接影响首屏
减少资源大小 优化图片格式与尺寸、压缩 CSS/JS、开启 gzip/brotli 传输体积是加载耗时的第一要素

减少 DNS 查询 减少不同域名数量、使用 dns-prefetch DNS 解析有几十到几百毫秒
首屏优化 关键 CSS 内联、JS 加 defer/async、图片懒加载、路由按需加载 让用户更快看到内容
协议升级 开启 HTTP/2 多路复用、启用 HTTPS + TLS 1.3 减少连接建立与队头阻塞
服务端 加缓存（Redis）、优化慢 SQL、加索引、上集群 缩短 TTFB

名称 层级 平台 语言绑定 用途与特点

    因为我在 github 初始化仓库时勾选了 README，这样就导致远程仓库比本地多了一个文件。根据报错执行 pull origin master 时报 fatal: refusing to merge unrelated histories. 然后接下来主角出场：git pull origin master --allow-unrelated-histories

  4. 编译安装 phalcon 扩展，make install 之后 make test 报错

    问题原因：扩展加载顺序导致，正常情况下应先加载 json.so 后加载 phalcon.so

  5. 编译安装 php 时未指定 --with-config-file-path —— 后期安装 redis 等扩展后一直未生效，查看 phpinfo() 输出信息 Configuration File (php.ini) Path 和 Loaded Configuration File 选项是否和手动复制的 php.ini 路径一致，不一致则改为一致。

  1. 区块链 —— 原文

    • 本质：区块链是一个去中心化的分布式账本，由一串按时间顺序链接的区块组成，每个区块保存一批交易记录。
    • 四大核心技术：① 哈希链（每个区块存前一个区块的哈希，改动任一区块会导致后续全部失效）；② 非对称加密与数字签名（证明交易由私钥持有者发起）；③ 分布式共识（PoW 工作量证明 / PoS 权益证明，解决”谁来记账”）；④ P2P 网络（节点互相同步，无中心服务器）。
    • 关键特性：不可篡改、可追溯、去中心化、公开透明（公有链）。
    • 不可能三角：去中心化、安全性、可扩展性三者难以同时最优，这也是各类公链方案权衡的核心。
    • 局限：吞吐量低（比特币约 7 TPS）、确认延迟高、能耗大（PoW）、智能合约漏洞风险、私钥丢失即资产丢失。

  2. Activiti 与 BPMN2.0 规范 —— 原文

    • BPMN 2.0（Business Process Model and Notation）是 OMG 组织制定的业务流程建模与标记法标准，用图形化的方式描述业务流程，同时定义了标准的 XML 交换格式，使不同工具之间可以互通。
    • Activiti 是一个轻量级的 Java 工作流引擎，遵循 BPMN 2.0 规范，把画好的流程图（.bpmn）部署到引擎中，由引擎驱动流程流转、分配任务、记录流程实例状态。
    • 核心概念：
概念 说明
ProcessDefinition 流程定义，一次部署的流程图模板
ProcessInstance 流程实例，按定义跑起来的一次具体流程
Task 任务，需要人（UserTask）或系统（ServiceTask）处理
Gateway 网关，决定流程分叉与合并（排他/并行/包容）
Event 事件，开始、结束、边界、中间捕获/抛出事件
  1. 如何做好需求分析和设计？ —— 原文
    • 需求分析四步：① 明确业务目标（这个需求解决什么问题、怎么衡量成功）；② 识别角色与场景（谁用、在什么情况下用、完整流程是什么）；③ 梳理功能与非功能需求（性能、并发、安全、兼容性）；④ 确认边界与优先级（哪些不做、哪些先做）。
    • 设计阶段的关注点：领域模型（表结构、实体关系）→ 接口设计（API 契约、入参出参、错误码）→ 流程与状态机（关键业务的状态流转）→ 异常与边界（失败重试、幂等、回滚）→ 监控与灰度（上线后怎么看效果、怎么回退）。
    • 质量判断标准：需求文档让测试能直接写用例、接口文档让前端能直接联调，说明分析到位了；否则就是还有歧义没消除。
