empty 与 isset

1 核心区别

判断函数 实际在问什么 判定为真的条件
isset($v) 「$v 是不是 null」 变量存在 且 值 !== null
empty($v) 「$v 是不是假值」 变量不存在，或 值属于假值集合

一句话记忆：isset 只认 null 这一个敌人，empty 把所有假值都当敌人。

2 全值域对照表

值 isset() empty() 说明

null false true isset 和 empty 的分水岭

' '（空格） true false 空格不算空
'0.0' true false
[]（空数组） true true
[0] true false 有元素就不算空
new stdClass()（无属性对象） true true 无属性对象算空
对象有属性 true false
资源 fopen(...) true false 资源恒非空

⚠️ 最坑的两个：

  1. '0'（字符串零）会被 empty() 判为空。判「非空字符串」要写 $v !== '' && $v !== '0'，或者直接 $v !== '' 加上 trim()。
  2. 无属性的对象也被 empty() 判为空。$user = new User(); empty($user) → true，哪怕对象本身存在。

`isset($a) && isset($b)

isset($a, $b) === true 明确优先级，避免误读

项 isset() empty()

嵌套安全 ✅ 内部任一层不存在直接返回 false，不报 warning ✅ 同左，且返回 true

include 与 require

1. ❗ 修正笔记错误

❌ 笔记错误：「include 在用到时加载，require 在一开始就加载」——这是错的。

事实 说明
include 和 require 都在语句所在的那一行加载 文件里写第 10 行，就执行到第 10 行才加载
真正决定「只加载一次」的是 _once 后缀 include_once / require_once
两者唯一的区别是失败后的行为 include 报警告继续跑，require 致命错误停止

2 四个变体总表

写法 加载时机 文件缺失时 是否重复加载
include 执行到该语句时 E_WARNING，继续执行，返回值 false 会重复
include_once 执行到该语句时 E_WARNING，继续执行 已包含过则跳过
require 执行到该语句时 E_ERROR（致命），立即终止整个脚本 会重复
require_once 执行到该语句时 E_ERROR，终止脚本 已包含过则跳过

💡 区分「加载时机」：只有在函数内且延迟调用的写法，文件才会真正「用到时」加载——但那是代码写法决定的，不是 include vs require 的区别。

3 返回值

项 include / require
被包含文件有 return 返回该值
被包含文件无 return 或 return; 返回 int(1)
文件不存在 include → false；require → 致命错误不会执行到

4 路径与作用域

项 规则
相对路径基准 先查 include_path（含 .），再查当前脚本所在目录，再查调用脚本所在目录，最后查工作目录
路径含 / 时 会被当作普通相对路径，不再查 include_path
变量作用域 被包含文件继承调用处的作用域；函数和类定义在包含后全局可见（除非在函数内定义）
$GLOBALS 可在配置文件里用它给全局赋值

风险 说明 防护

本地文件包含（LFI） 可读任意文件，配合上传即 RCE 同上 + 禁用户可控路径

6 与 eval、autoload 的关系

机制 用途
include / require 手动引入文件
include_once / require_once 手动引入 + 防重复

传值与传引用

1 基本概念

方式 语法 形参与实参关系 改形参影响实参
传值 function f($x) 值副本 ❌ 不影响
传引用 function f(&$x) 同一个变量（别名） ✅ 影响

2 ❗ 关键补充：对象是特例

笔记漏了最重要的一条：对象永远传句柄，不存在「传对象值 / 传对象引用」的区分。

情况 修改影响实参？
改对象的属性 $obj->p = x ✅ 影响（对象是引用语义）
给形参重新赋值 $obj = new X ❌ 不影响（只是改了局部变量指向）
改数组的元素 $arr['k'] = x ❌ 不影响（数组是值语义，除非传引用）

3 写时复制（COW）

项 说明
全称 Copy-On-Write
行为 传参时不立即拷贝，只是引用计数 +1；只有形参被写入时才真正复制一份
好处 只读参数零拷贝，性能好、内存省
副作用 $a = ['x' => 1]; $b = $a; 后 $a 和 $b 内存地址相同，但改一个不影响另一个

4 数组与对象对照（最容易混的地方）

类型 传参语义 改属性/元素 重新赋值
标量（int/string/bool/float/null） 值 — 需 &
数组 值（COW） ❌ 需 & 需 &
对象 句柄 ✅ 直接生效 ❌ 不生效（& 也不行）
类实例 & 句柄 + 变量引用 ✅ ⚠️ 可改形参的指向

5 引用作为返回值

位置 含义
参数前的 & 按引用传参
返回类型前的 & 返回引用，调用方可用 =& 接收并修改源变量
调用方的 =& 接收引用（等价于引用赋值）

⚠️ 引用返回极易产生「意外修改」和循环引用，现代 PHP 基本不该用。

6 引用相关的常见坑

foreach 不加引用 改 $v 不影响数组 值遍历 foreach ($arr as $k => &$v)
foreach 加引用忘了 unset 后续循环把上一个元素改坏 引用残留 循环体末尾 unset($v)，必须
引用了不存在的变量 自动创建并变 null 引用赋值的特性 传引用前先 isset() 判断
形参默认值不能是引用 语法错误 — 用 ?array $x = null + 内部处理

抽象类和接口

零、笔记错误速览（先看这个）

# 笔记原文 问题 修正
1 「接口是一种特殊的抽象类」 ❌ 概念性错误。接口和抽象类是并列的两种类型，接口不是抽象类的子类。两者只是语法长得像（都用 {} 声明、都可声明未实现的方法），且在 PHP 里互不能转换 二者是「抽象的两种方式」，不是「父子关系」
2 「接口没有数据成员」 ⚠️ PHP 8.4 起过时。自 PHP 8.4.0 接口可以声明属性（须配合 property hooks 指定 get/set 需求） PHP ≤ 8.3 无属性；≥ 8.4 可声明属性契约
3 「接口没有构造方法」 ⚠️ 不准确。接口中可以声明 __construct()，只是 PHP 官方强烈不建议 不是禁止，是「不要这么写」

为什么第 1 条重要： 很多人以为「接口是抽象类的子类」，于是想 abstract class A implements I 这种写法，或者以为抽象类能当接口用。实际上：

误解 事实
接口是抽象类的子类 ❌ 二者无继承关系，interface 不能 extends 抽象类
抽象类可以实现接口的方法 ✅ 可以，abstract class X extends Y implements Z {} 完全合法
接口可以 extends 接口 ✅ 可以（笔记没提到）
接口可以被实例化 ❌ 不能，和抽象类一样

一、核心对比表

对比项 抽象类（abstract class） 接口（interface）
声明关键字 abstract class interface
能否实例化 ❌ 不能 ❌ 不能
能否有属性（成员变量） ✅ 有，可任意修饰符 ⚠️ PHP ≤8.3 无；8.4+ 可声明属性契约
能否有常量 ✅ 有 ✅ 有（8.1+ 可被覆盖）
能否有构造函数 ✅ 有，且常用于初始化 ⚠️ 可声明但强烈不建议
能否有方法实现 ✅ 可有（具体方法） ❌ 全为抽象（无方法体）
能否有抽象方法 ✅ 有 ✅ 全都是
方法可见性 public / protected / abstract 只能 public
抽象方法能否 private ❌ 不能（写 private abstract 报错） ❌ 概念不存在
继承方式 extends（最多一个） implements（可以多个）
能否被接口继承 — ✅ interface B extends A

二、笔记逐条修正

2.1 「抽象类的继承使用 extends，接口用 implements」

✅ 正确，但笔记不完整。补充：

场景 语法 说明
类继承抽象类 class B extends A {} 只能一个
类实现接口 class C implements I {} 可以多个，逗号分隔
同时继承 + 实现 class D extends A implements I, J {} 最常用组合
接口继承接口 interface B extends A {} 笔记没提
接口继承多个接口 interface C extends A, B {} 注意：extends 在接口间可以多个

💡 记忆点：extends 在接口之间是多个，在类之间是一个。这是唯一打破「extends 只能一个」的地方。

2.2 「抽象类有数据成员，接口没有」

版本 抽象类 接口
PHP ≤ 8.3 有属性 ❌ 不能有属性
PHP 8.4+ 有属性 ✅ 可声明属性契约

PHP 8.4 新增的接口属性：

规则 说明
必须声明 get 还是 set 不能只写 public string $name;——必须写 { get; } / { set; } / { get; set; }
接口声明只约束 public 读写 内部可见性实现类自定
{ set; } 的属性不能用 readonly 实现 冲突
{ get; } 可以用 readonly 满足 ✅ 允许

⚠️ 这是 PHP 8.4 才有的能力。如果你项目跑在 8.3 或更低，接口依然不能有属性。

2.3 「抽象类可以有构造方法，接口没有」

❌ 不准确。接口可以声明 __construct()，只是官方强烈不建议。

官方不建议的三个理由：

理由 说明
大幅降低实现类的灵活性 一旦接口要求构造签名，所有实现类都得照抄，无法用不同参数初始化
构造器不受继承规则强制约束 接口要求了，但没人能保证实现类的构造行为一致 → 行为不可预期
类型提示已够用 构造参数约束用具名类型表达，不需要塞进接口

正确做法： 把初始化逻辑抽成普通方法或工厂方法。

用途 说明

七、面向接口编程的优缺点

7.1 优点

优点 说明
结构清晰 类与实现解耦，阅读代码只需看接口

多重实现 弥补单继承的限制（一个类只能有一个父类）

7.2 缺点

缺点 说明
设计复杂度上升 差的接口设计会波及所有实现方，牵一发而动全身
并非所有场景都需要 系统简单时接口只是纯增工作量

层面 实际情况
理论 接口方法调用比直接调用多一层查表

7.4 什么时候不该用接口

反模式 问题
只有一种实现且不打算换 过度设计
接口只有一个实现类 YAGNI，等第二种出现再加
为了「规范」给所有类配接口 淹没真正的抽象
接口方法超过 10 个 它已经不是接口，是「上帝类」
接口里塞业务逻辑描述 接口只说「要什么」，不说「怎么做」

💡 判断标准： 问自己「我将来会换掉这个实现吗？」会 → 用接口；不会 → 抽象类或普通类。

一、封装（Encapsulation）

1.1 定义

项 说明
本质 把属性和操作属性的方法组织成一个整体（类），并通过访问控制符限制外部访问
目标 ① 保护内部数据不被随意篡改 ② 隐藏实现细节，调用方只依赖公开接口 ③ 允许内部自由修改实现而不影响外部

1.2 访问控制符

修饰符 本类 同类实例 子类 外部
public ✅ ✅ ✅ ✅
protected ✅ ✅ ✅ ❌
private ✅ ✅ ❌ ❌
无（默认） = public = public = public = public

💡 同类实例之间可以访问彼此的 private——因为它们是同一个类。判断依据是类，不是对象。

1.3 为什么用 getter/setter

如果不用封装 后果
public float $balance 外部可写 $account->balance = -99999，直接破坏业务规则
public 但只有 getter 调用方无法初始化，只能靠构造器

封装的三层含义：

层 做法
数据封装 private / protected 属性
行为封装 只暴露必要的 public 方法
校验前置 setter 里做合法性检查，非法数据进不来

1.4 封装的边界：不是万能钥匙

过度封装 问题
每个属性都写 get/set，内部什么都不做 纯样板代码，没实际价值
属性设 private 但 __get 里原样返回 假封装，外部照样能改
暴露内部可变数组引用 调用方改了内部状态

💡 现代实践（PHP 8.4+）：属性 hooks 和非对称可见性可以替代大量样板 getter/setter。

二、继承（Inheritance）

2.1 定义与语法

项 说明
本质 从已有类（父类）派生出新类（子类），子类继承父类的属性和方法
关键字 extends
单继承 一个类只能有一个父类（PHP 的限制）
子类可以做 加新属性、加新方法、重写父类方法

2.2 继承了什么

成员 是否继承 说明
public 属性与方法 ✅ 完全继承
protected 属性与方法 ✅ 子类可访问
private 属性与方法 ❌ 子类看不到
final 类/方法 ❌ 不允许继承/重写
构造函数 __construct 不会自动继承 子类定义了就必须调 parent::__construct()
析构函数 __destruct 不会自动继承 同上，需显式 parent::__destruct()
静态属性 ✅ 但共享同一份值（除非 8.3+ trait 场景）

2.3 构造链与析构链

规则 说明
构造顺序 父类先构造（parent::__construct() 通常写在子类构造函数第一行）
析构顺序 父类后析构
不调 parent:: 父类的构造/析构被完全跳过，不是「隐式调用后再覆盖」
父类无构造函数 调 parent::__construct() 会 Fatal error（除非自己声明了空构造）

⚠️ 经典坑：class Child extends Parent 但 Parent 没有 __construct，子类里写了 parent::__construct() → 致命错误。这是 PHP 里最常见的继承坑之一。

规则 说明
可见性不能缩小 父类 public → 子类不能改 protected/private（会报错）
可见性可以放大 父类 protected → 子类可以改 public ✅

2.5 继承的代价（组合优于继承）

问题 说明

紧耦合 子类被迫继承不需要的东西
层次僵化 单继承限制了类结构自由度
难以测试 子类为了测一个方法要实现整个父类契约

什么时候用继承： 「is-a」关系且确实需要替换实现（如 MySqlRepository extends AbstractRepository）。

三、多态（Polymorphism）

3.1 定义

⚠️ 笔记定义偏窄：「一个父类被多个子类继承，父类的某个方法在多个子类中表现出不同的功能」——这只是多态的一种表现（重写多态）。多态在 PHP 里主要有三种实现路径，且接口多态才是现代 PHP 的主流。

实现方式 机制 是否需要继承 现代价值
重写（override） 子类重写父类方法 ✅ 需要 中（模板方法模式）
接口多态 不同类实现同一接口 ❌ 不需要 高（主流）
参数多态 方法参数声明为类型（接口/父类），运行时传入不同对象 — 最高（现代 PHP 主流）

3.2 参数多态（重点：现代 PHP 怎么用多态）

💡 这才是多态的价值所在：调用方代码不随实现变化而变化。笔记里的「父类方法在子类表现不同」只是最朴素的形式，真正的收益是「一处调用，多种实现」。

3.3 运行时多态的实现原理

步骤 发生了什么
1 foreach 遍历数组，每个元素实际类型不同
2 调用 $a->speak()，PHP 在运行时查这个对象真实类型
3 找到对应的实现并执行
4 返回各自不同的结果

关键：编译时不需要知道具体类型。 这就是「运行时的多态」，和 Java/C# 的机制一致。

3.4 三种多态的对比

场景 重写多态 接口多态
代码量 少（共用父类属性） 多（每个实现都写一遍）
耦合度 高（子类必须继承父类） 低（只依赖契约）
可替换性 差（要重新继承链） 好（换实现不改调用方）
适用 模板方法、共享状态 支付/存储/日志等可插拔组件

3.5 判断多态是否用对

症状 问题 正确做法
大量 if ($obj instanceof X) 用类型判断代替了多态 参数声明为接口，让调用方决定
多个方法签名都写同一组类型 没抽接口 定义 GatewayInterface
换了实现要改多处调用代码 耦合没解 接口 + 依赖注入

4.1 PHP 不支持真正的多重继承

语言 多重继承
Java / C# / PHP ❌ 单继承（一个类只能有一个父类）
C++ / Python / Ruby ✅ 支持多继承

PHP 的替代手段：

方案 提供什么 是否共享实现

💡 组合记忆：接口解决「多继承关系」，trait 解决「多复用实现」。接口给契约，trait 给代码。

五、Trait 详解

5.1 是什么

项 说明
定义 PHP 5.4 引入的代码复用机制
本质 「有编译器帮忙的复制粘贴」 —— 官方原话
关键词 use（类体内，和命名空间的 use 不是一回事）
能否实例化 ❌ 不能，它不是类
能否继承 ❌ 不能被 extends
核心价值 在没有继承关系的多个类间横向复用代码

5.2 基本用法

语法 说明
use TraitA; 混入一个
use TraitA, TraitB; 混入多个（逗号分隔）
use TraitA, TraitB { ... } 带冲突解决

5.3 Trait 的三个「魔法」特性

① 能访问宿主的私有成员

这是 trait 相比普通组合类的重要优势：它真正”长”在宿主类里。

② __CLASS__ 返回宿主类名

③ 可以组合 trait

5.4 优先级顺序（最常考，也最常错）

场景 谁赢
类自己写了同名方法 类自己赢（trait 被静默忽略，不报错）
trait 与父类同名方法 trait 赢
两个 trait 同名方法 ⚠️ Fatal error，必须显式解决

⚠️ PHP 8.5 有变更：

版本 trait 与父类都有同名属性/常量时
PHP ≤ 8.4 Fatal error（不兼容的组合）
PHP 8.5+ trait 优先，覆盖父类继承的成员

这更贴近 trait 的「复制粘贴」语义。方法解析规则不变（trait 一直覆盖父类方法），变的是属性和常量。

5.5 冲突解决：insteadof 与 as

两个 trait 有同名方法时，不解决直接 Fatal：

方案一：insteadof 二选一

方案二：insteadof + as 两个都要

方案三：as 改可见性

操作符 作用 注意
insteadof 冲突时选用哪个，排除另一个 只能排除，不能改名
as 给方法起别名 ⚠️ 不改变原方法名，也不影响其他方法
as + 可见性 as protected / as private 单独用 as 也可以

💡 排查冲突的实用技巧： 用反射把 trait 方法全打出来对比，不用猜。

5.6 属性的冲突规则（比方法严格）

场景 结果
两个 trait 声明同名属性 必须完全一致（可见性 + 类型 + readonly + 默认值），否则 Fatal
PHP 8.2+ 允许只声明类型不给默认值，但两边类型仍须一致
类定义了与 trait 同名属性 同上，兼容性检查

5.7 trait 中的抽象方法（强制约束）

版本 支持的抽象方法可见性
PHP < 8.0 仅 public / protected
PHP ≥ 8.0 public / protected / private 都支持

8.0 起的签名规则： 具体方法的签名必须符合兼容性规则（此前可以不一致）。

💡 这是 trait 里做接口约束的好办法：trait 提供流程，抽象方法定义宿主必须提供什么。

5.8 trait 中的静态成员

项 说明
静态变量/方法/属性 ✅ trait 可定义
静态属性：每个用该 trait 的类是独立副本 和继承的共享语义完全不同
直接在 trait 上访问静态成员 PHP 8.1+ 起弃用，必须通过类访问

静态属性对比（重要）：

⚠️ PHP 8.3 起又改了：如果子类自己也用了同一个 trait，它与父类的 trait 静态属性视为不同的。8.3 之前同一继承层次里是共享的。

5.9 trait 版本能力时间线

版本 新增能力

class C { use T; final public function f() {} } ✅ 类自己声明，覆盖 trait

六、Trait vs 继承 vs 接口 vs 组合

6.1 四选一决策表

机制 提供 关系 何时选
继承 extends 属性 + 方法实现 + 契约 is-a，单继承 确实是父子类型关系，需替换实现
接口 implements 仅契约 can-do，可多个 声明能力，让实现可插拔

三、ob函数

概念

  1. 当PHP脚本有输出时，输出控制函数可以用这些来控制输出。这在多种不同情况中非常有用，尤其是用来在脚本开始输出数据后，发送http头信息到浏览器。输出控制函数不影响由header()或setcookie()发送的文件头信息，仅影响像echo这样的函数和PHP代码块间的数据。

  2. 常用函数

函数名称 含义
ob_start(); 打开一个输出缓冲区，所有的输出信息不再直接发送到涉猎器，而是保存在输出缓冲区里面
ob_clean(); 删除内部缓冲区的内容，不关闭缓冲区(不输出)
ob_end_clean() 删除内部缓冲区的内容，关闭缓冲区(不输出)
ob_get_clean() 返回内部缓冲区的内容，关闭缓冲区。相当于执行ob_get_contents()和ob_end_clean()
flush(); 将ob_flush释放出来的内容，以及不在PHP缓冲区中的内容，整个输出至涉猎器；刷新内部缓冲区的内容，并输出
ob_flush(); 发送内部缓冲区的内容到涉猎器，删除缓冲区的内容，不关闭缓冲区
ob_end_flush() 发送内部缓冲区的内容到涉猎器，删除缓冲区的内容，关闭缓冲区
ob_get_flush() 返回内部缓冲区的内容，并关闭缓冲区，再释放缓冲区的内容。相当于ob_end_flush()并返回缓冲区内容
ob_get_contents() 返回缓冲区的内容，不输出

  1. 输出控制存在的意义：因为http协议的限制(前几行必须是协议信息，然后一个空行，然后才是用户需要的内容，需要保证header信息在其他内容之前发送，否则浏览器无法解析服务器返回的内容。

五、register_shutdown_function

  1. register_shutdown_function(callable $callback[, mixed $parameter[, mixed $... ]]):void，注册一个callback，它会在脚本执行完成或者exit()后被调用。可以多次调用register_shutdown_function()，这些被注册的回调会按照他们注册时的顺序被依次调用。如果你在注册的方法内部调用 exit()，那么所有处理会被中止，并且其他注册的中止回调也不会再被调用。

  2. Note

    • 在某些web server(如Apache)上，可以在中止函数内对脚本的工作目录进行修改。
    • 如果进程被信号SIGTERM或SIGKILL杀死，那么中止函数将不会被调用。尽管你无法中断SIGKILL，但你可以通过pcntl_signal()来捕获SIGTERM，通过在其中调用exit()来进行一个正常的中止。

  3. 基本用法，和别的注册回调没太大差别

七、str_replace

  1. 功能：子字符串替换

  2. 用法：str_replace(mixed $search, mixed $replace, mixed $subject[, int &$count ]): mixed

  3. 说明：该函数返回一个字符串或者数组。该字符串或数组是将subject中全部的search都被replace替换之后的结果。

    • 如果search和replace为数组，那么str_replace()将对subject做二者的映射替换，它们的值将会被依次处理。
    • 如果replace的值的个数少于search的个数，多余的替换将使用空字符串来进行。
    • 如果search是一个数组而replace是一个字符串，那么search中每个元素的替换将始终使用这个字符串。

  4. 参数

    • search：查找的目标值，也就是 needle。一个数组可以指定多个目标。
    • replace：search 的替换值。一个数组可以被用来指定多重替换。
    • subject：执行替换的数组或者字符串。也就是 haystack。如果 subject 是一个数组，替换操作将遍历整个 subject，返回值也将是一个数组。
    • count：如果被指定，它的值将被设置为替换发生的次数。

CGI · FastCGI · PHP-CGI · PHP-FPM

零、笔记错误速览

原文 修正
「php-fpm 会开启多个 php-cgi 程序」 FPM 的 worker 就是 php-cgi 二进制自身 fork 出来的子进程，同一个可执行文件，不是两个程序
「内存消耗过大引发 502」 502 的直接原因不是内存，是 worker 耗尽/超时导致 Nginx 拿不到上游响应。内存只是背后的推手
「FastCGI 则是一个进程可以处理多个请求」 FastCGI 只规定通信协议，是否复用进程由实现决定

一、一句话结论

名字 本质 一句话
CGI 协议 web server 和后端程序之间的通信规范，规定「传哪些数据、什么格式」
FastCGI 协议 CGI 的改良版，核心是进程复用（长驻，不再一请求一进程）
php-cgi 程序（SAPI） PHP 对 CGI 协议的实现，每次请求起进程、干完就退出
php-fpm 程序（SAPI） PHP 对 FastCGI 协议的实现，自带 master/worker 进程池

关系链：

二、为什么需要 CGI 这层协议

环节 发生了什么
静态请求（/index.html） web server 直接读文件系统，不经过任何解释器
动态请求（/index.php） web server 按配置把请求转交给对应解析器
转交时必须带的数据 URL 路径、查询字符串、POST 数据、HTTP Header、客户端 IP、端口…
CGI 管什么 规定「传哪些数据、什么格式」，让后端程序不用为每个 server 写一套适配

CGI 的原始动机是「让后端程序编写者能拿到标准格式的数据」，不是为了性能。它后来被 FastCGI 取代的原因只有一个：太慢。

三、CGI 慢在哪

维度 CGI（每个请求） FastCGI
进程模型 一请求一进程，处理完立即销毁 一进程多请求，处理完接着处理下一个
启动开销 每次都重新解析 php.ini、初始化 Zend 虚拟机 只在 master 启动时做一次，worker 直接复用
进程数随并发增长 并发 N → N 个 CGI 进程 并发 N → N 个 worker，由池大小封顶
内存/资源消耗 高，且频繁分配释放 稳，进程长期驻留
配置生效 每次请求重新读，天然实时 需重启（reload）才生效

FastCGI 的调度逻辑：

步骤 master 做什么
1. 启动时 解析配置文件、初始化执行环境
2. 启动时 预启动多个 worker 进程
3. 请求到达 交给某个空闲 worker，自己立即返回去接下一个
4. worker 不够 按配置预先启动备用 worker
5. worker 太多 回收多余 worker

⚠️ 常见误解：FastCGI 是协议，不是进程。就像 HTTP 是协议，Apache 的实现叫 httpd，Nginx 的实现叫 nginx。

五、逐个概念拆开

CGI（Common Gateway Interface）

项 说明
全称 Common Gateway Interface，公共网关接口
作用 让 web server 把动态请求 + 参数，以标准格式传给后端程序
类比 「插座标准」——规定插头长什么样，至于用电器是冰箱还是电视它不管
生命周期 每请求：启动进程 → 读配置 → 处理 → 输出 → 销毁进程
现状 已被 FastCGI 取代，PHP 里基本只作为历史概念出现

FastCGI

项 说明
本质 协议（不是进程）
改进点 进程复用 + 数据结构优化，把「每次初始化」变成「一次初始化」
实现者 php-fpm（官方）、spawn-fcgi（从 lighthttpd 分裂）、IIS FastCGI Handler 等
注意 协议不规定进程数，进程池大小由实现方配置决定（php-fpm 的 pm.*）

php-cgi

项 说明
定位 PHP 提供的 CGI 协议接口程序，就是 PHP 解释器在 CGI 模式下的运行形态
每次请求 启动进程 → 加载 php.ini → 初始化数据结构与运行环境 → 处理请求 → 按 CGI 格式返回 → 销毁进程
配置生效 改 php.ini 必须重启 php-cgi 才生效
致命短板 只是「一个干活的程序」，不会管理进程。高并发顶不住
于是有了 spawn-fcgi、php-fpm 这类「调度器」来 fork 和复用 php-cgi
现状 官方明确不推荐用于生产

php-fpm（PHP FastCGI Process Manager）

项 说明
全称 PHP FastCGI Process Manager
定位 实现了 FastCGI 协议的程序，已被 PHP 官方收录，目前的事实标准
与 php-cgi 的关系 可理解为 php-cgi 的管理程序 + 改进版：不随请求生死，常驻，一进程接多连接
工作方式 master 常驻内存 → 把请求分给某个 worker → worker 处理完不退出，继续等下一个
加速原理 省掉每次的「重载配置 + 初始化数据结构 + 初始化运行环境」
进程结构 master（管理） + N × worker（干活）；空闲 worker 超阈值会被回收

六、进程模型示意

模型 请求流向 生命周期
CGI nginx ──> [php-cgi 进程] ──> 结束销毁 进程寿命 = 单个请求寿命
FastCGI + spawn-fcgi nginx ──> spawn-fcgi ──fork─> [php-cgi]，进程复用 进程寿命 = 多请求
FastCGI + php-fpm nginx ──> [master 常驻] ──分派─> worker（复用） master 常驻，worker 复用

php-fpm 内部角色：

角色 数量 职责
master 1 读配置、监听 socket、分派请求、管理 worker 生命周期
worker N（pm.max_children 上限） 真正执行 PHP 代码、跑 Zend 虚拟机
idle worker 按参数调节 空闲回收，避免内存浪费

七、内存与 502 的真实关系

说法 是否准确 说明
「php-fpm 开启多个 php-cgi 进程」 简化说法 FPM 的 worker 本身就是 php-cgi 二进制的 fork 子进程
「一个 php-cgi 占 7~25M」 大致量级 实际取决于扩展、memory_limit、脚本复杂度；常见 RSS 在 20~40M
「内存涨太多会引发 502」 间接成立 502 的直接原因不是内存，而是 FPM worker 不够/超时导致上游无响应

502 的典型链路：

环节 现象 排查命令
FPM 进程数打满 请求排队 → 排队超时 pm.max_children 是否过小
pm.max_children × 单进程内存 > 物理内存 系统 swap / OOM，worker 被杀 看 free -h、容器 memory.limit
脚本执行超时 FPM 主动断开，Nginx 报 502 调 request_terminate_timeout
慢脚本 / 死循环 worker 被占满，后续请求全排队 request_slowlog_timeout + slowlog
真正的 OOM kernel 杀进程 Nginx error log 出现 worker process ... exited on signal 9

💡 排查顺序：先看 FPM 的饱和度，再看内存，最后才看代码。别一上来就加内存——pm.max_children 算错的话，加多少内存都会被吃光。

八、术语对照（最容易混的一组）

术语 在 PHP 里指什么
cgi 进程 / 线程 就是 php-cgi 进程/线程，专门接收 web server 的动态请求，调用并初始化 Zend 虚拟机

顺序 CGI 模式（php-cgi） FastCGI 模式（php-fpm worker）
1 启动进程 worker 已常驻（首次启动时初始化一次）
2 解析 php.ini 跳过（已加载）
3 初始化数据结构 + Zend VM 环境 跳过（已初始化）
4 解析脚本 → 编译 opcode → 执行 同左
5 按 CGI 格式输出结果 同左
6 销毁进程 回到池中等待下一个请求

九、常用误区纠正

常见说法 实际情况
「FastCGI 是一个进程」 ❌ FastCGI 是协议，php-fpm 才是实现它的程序
「php-fpm 和 php-cgi 是两个不同的可执行文件」 ❌ 都是 PHP 的 SAPI 形态；FPM 的 worker 就是自身 fork 出来的子进程
「FastCGI 规定了一进程多请求」 ⚠️ 不准确。FastCGI 只规定通信协议，是否复用进程由实现决定
「用了 FastCGI 就一定不重启」 ❌ FPM 改 php.ini / www.conf 仍需 reload
「CGI 慢是因为语言慢」 ❌ 慢在进程创建销毁 + 每次重复初始化环境，与语言本身无关
「php-cgi 现在还能用」 能，但不推荐生产；官方推荐 php-fpm

❌ 「foreach 比 for 快 1 倍」 ✅ 反了：需要操作数组时，for 反而比 foreach 快（8.4 下 1.39ms vs 1.86ms）
❌ 「array_walk 比 foreach 快 43%」 ✅ 反了：8.4 下 array_walk（4.00ms）比 foreach 值（1.86ms）慢一倍多
❌ 「循环内调用函数 array_walk 最好」 ✅ 反了：直接内联代码（for 直接写 1.39ms）比任何函数封装都快
✅ 「不要在深循环里调用函数」 ✅ 依然正确，且差距比 2017 年更大（3.3ms vs 1.4ms，约 2.4 倍）

二、为什么会翻转

原因 说明
Zend Engine 3 优化了数组访问 PHP 7 引入 AST + 优化后的 opcode，$arr[$i] 的哈希查找成本大幅下降，for 循环的劣势被抹平
opcache 默认启用 编译期开销被摊薄，循环本身的差异凸显出来
PCRE JIT / 内建函数优化 array_walk 的回调调用无法被内联优化
回调调用成本被放大 PHP 8 每次用户函数调用都有更严格的参数类型检查，array_walk 的间接调用最吃亏

💡 历史原因：2017 年 for 循环每次 $arr[$i] 都要走哈希表查找，而 foreach 直接用内存指针顺序遍历，所以差距明显。PHP 7 之后这个优化被大幅压缩，差距从「2 倍」变成「几乎打平甚至反超」。

三、正确的性能排序（本机 PHP 8.4）

排名 写法 耗时 说明

五、array_walk 的三个硬限制

限制 说明 后果
回调必须按引用声明 function cb(&$item) 不能写成 function cb($item) 传值时 PHP 报 Notice，PHP 8+ 更严格

内部函数不适用 回调必须是用户函数或有效的 callable array_walk($arr, 'strtoupper') 会报错

PHP 执行代码的四个步骤

零、原文四步骤总结

一句话记忆：词法 → 语法 → 编译 → 执行，对应编译原理的前端 + 后端。

一、步骤详解

步骤 名称 做什么 输入 → 输出 失败表现
1 Scanning / Lexing 把源码切成一个个「词」 .php 源码 → Tokens 数组 几乎不失败
2 Parsing 把 Tokens 组装成表达式 Tokens → AST（抽象语法树） 抛 ParseError
3 Compilation 把 AST 转成可执行指令 AST → Opcodes 抛 Error
4 Execution 逐条执行指令 Opcodes → 输出结果 抛各种 Exception / Error

📌 注意 PHP 7 的变化：原文（基于 PHP 5）里第 2 步 Parsing 是「转换成简单表达式」，第 3 步直接编译成 opcode。PHP 7 引入 AST 后，Parsing 阶段会先生成一棵完整的抽象语法树（AST），Compilation 再遍历 AST 生成 opcode。中间多了一层，但换来了更好的优化能力。
